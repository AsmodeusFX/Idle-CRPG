# 01｜战斗目标选择与无碰撞接敌：完整规则 V1.0

> 对象：Steam D2 自动小队挂机 ARPG / Godot 4.7 .NET C# / Game.Core 与 Game.Godot。  
> 性质：**用户已确认规则（C）+ 执行提议（R）+ 待工程核实/审批（T）**；以逐条标注为准。  
> 重要：这是一份**对现有工程的增量方案**，不是新战斗引擎设计授权。实施须先通过 `02_Preflight_Conflict_Gate.md`。

## 0. 目标、边界、验收观感

**目标**：坦克先进房、自然而稳定地接住有限近战怪；超出容量的怪陆续绕向后排；普通远程怪优先攻击最近合法目标；嘲讽/救场是特殊技能；无真实单位物理碰撞但敌群能在画面中自然展开。坦克容量提升后，正常情况下有更多敌人由坦克承接，效果一目了然。

**不做**：WoW 式伤害/治疗仇恨账本、每 Tick 全体怪重新排序、全体均摊/压力平衡公式、无限距离自动守护、依靠刚体把敌人挡在门口、战斗与地图/装备/掉落/经验系统重写。

**约束**：房间制战斗、自动 AI、多个可上阵职业（首版4人上限，长期5人）、召唤物、主动技能/被动效果、固定 Tick 的 Core 权威与确定性测试；尊重当下真实 Godot 工程实现。用户已选“全部推荐项”，但仍需核实旧合同与当前代码。

## 2. 三个独立概念：攻击合法性、近战接敌占用、当前锁定

**2.1 攻击合法（Attackable）**：对象存在、为敌对阵营、存活或满足该攻击的可攻击状态、在当前战斗/房间内；射程和活动边界按当前 Attack/Skill/Movement 合同分别判定。**容量满/容量为0从不让一个目标变成“不可攻击”**。

**2.2 近战接敌容量（EngagementCapacity）**：一名战斗单位可为普通近战敌人提供的**优先正常占用名额**。非负整数；0表示不主动容纳近战，不意味着免疫近战伤害或不能被目标锁定。示例：野蛮人3、圣骑士5、骷髅1、法师0（均为 **测试样例**）。仅正在使用近战攻击意图的敌人参与；远程投射物、远程法术和纯AOE不占。

**2.3 目标锁定（TargetLock）**：怪物当前追逐/普通攻击对象；与某个技能临时的特定 TargetPolicy 分离。建议锁定带**原因**，而不是把“目标是否存在”和“有没有正常容量”混为一谈：

- `Normal`：当前目标接敌槽位有效，已预占一个。
- `Overflow`：正常槽位未取得，但为了不中断战斗，可以追击/攻击合法目标；允许在合法时机重新找更合适目标。
- `Forced`：受到嘲讽/救场技能的强制锁定，有明确持续时限/终止条件；独立于普通容量资格。

这些是**建议的运行态标签，不是硬要求另建一套实体系统**；如果现有 Actor/AI Runtime 已含等价状态，应映射复用。`Normal` 仅指普通近战接敌；普通远程攻击可以保持自身正常主目标锁定，**不创建或消耗近战容量槽位**，无需将远程怪也强塞进这三个标签。

## 3. 近战目标初选：确定性两段法

**第一阶段：正常容量槽。** 对一个需要目标的普通近战怪：

1. 构建**当前已发现、存在且合法、可在允许追击边界内接近**的敌方单位候选；容量>0才进入“正常槽候选”。
2. 若存在有空位的正常槽候选，按**现有已确认的自然距离/合法性排序**优先选择，原有相等排序若未定则进入审计待确认。若前排距离明显不合理，不能跨整房间强行吸怪；合法追击范围必须复用工程已有约束。
3. **同一 Tick** 以稳定顺序逐只预占槽位；怪物锁定目标、标注 `Normal`，随后按照现有 ActionRequest/Movement 行动。

**第二阶段：临时溢出。** 当没有可取得的正常槽，或周围没有合法槽位候选：

1. 优先找合法、已发现的其他目标（例如基础容量为0的法师/游侠），按**最近有效目标**选择；**容量0的后排没有“一对一名额限制”，可同时承受多只怪**。
2. 若没有其他合格目标（如只有野蛮人已进场），可以超额锁定已满坦克并立即继续攻击，标记 `Overflow`。
3. **禁止**因为容量不足而产生 `WaitUntilSlotAvailable` 或循环尝试无合法目标的卡死行为。
4. 如果已经正常分配的其他目标出现，也只能在合规的动作边界处理；不会因为法师造成高伤害就自行生成仇恨值重新锁定。

> **重要：同队全员容量都是0的合法情况**（初始法师单人、四输出阵容）。这时跳过第一阶段，直接最近有效目标；**不让全队变为不可索敌**。

> **重要：如果有两名坦克、其中一名有余量**，优先尝试其合法接敌槽；但不允许不顾距离跨越整个房间吸怪。精确“范围门槛/并列排序”要审计现有机制并用 Demo 调参，不私设正式数值。

## 4. 进门与“坦克先出现”的时间线

**不设置明显的怪物停机等待。** 坦克先入门后，怪物只看得到/只把其当成合法目标时，允许立即锁定坦克；正常槽被依次预占，其余暂为 `Overflow`。当其他队员进入可被索敌的活动区域时，系统在固定 Tick 上生成 `CandidateSetChanged` / 等价事实，**安排**超额怪重新评价。

示例：野蛮人容量3，房内8近战怪。

| 时刻 | 坦克 | 后排 | 结果 |
|---|---|---|---|
| T0 仅坦克入场 | 3个 Normal + 5个 Overflow | 不在合法候选 | 8只怪可以正常追击/攻击；不等待 |
| T1 法师入场 | 原3个 Normal 不动 | 法师基础容量0 | 超额怪可在安全边界寻找法师；**不限于只转1只** |
| T2 游侠入场 | 原3个 Normal 不动 | 法师/游侠均为有效目标 | 余下 Overflow 怪按最近合法非满坦克目标转移，**不刻意均摊** |
| T3 队伍全部进入 | 坦克仍承接已正常接敌单位 | 其他近战怪可能集体围攻更近后排 | 后续只有必要事件才再次重评 |

**修正历史误区**：后排容量为0，故“法师入场只增加1个容量，让1只怪转向法师”**不是最终规则**。法师成为一个**不限近战攻击者数量**的合法溢出目标（几只追法师取决于谁发现他、距离/射程与稳定锁定约束）。

**状态触发与动作边界**：新队友入场、召唤物出现、目标死亡/消失、原目标失去可攻击性、普通槽位释放、强制目标效果结束、AI原锁定失效、长时间无法有效接近等可产生 `NeedsReevaluation`。该标记由当前固定 Tick/Action Runtime 在**安全决策边界**消费；**不在事件监听器中同步递归 AI，不在 Windup/Commit 过程里凭空转身取消技能**。若攻击已提交且不可中断，先完成合法攻击再迁移目标。

**避免抖动的最简原则**：正常接敌不参与主动负载均衡；溢出怪在“新目标明显可用”时可以换一次，换后保持至少到下一合法重评边界；同一帧仅安排有界数量处理，选择顺序稳定。无需新增复杂的“最佳目标收益公式”；行动稳定时长、重新评价间隔等**待真实工程审核及实机调参**。

## 5. 容量释放、动态变化、目标重选

- **怪物死亡或离场**：释放其先前的 `Normal` 接敌预约，保证每个怪物最多持有一份、释放至多一次；移除原 `Overflow` / `Forced` 状态。
- **目标死亡/消失**：该目标不再合法，所有锁定它的怪安排重新索敌；未完成技能按既有动作生命周期规范处理；不得引用已注销实体。
- **角色/召唤物新加入**：仅触发需要寻找新目标的 `Overflow` 怪的重评，当前 `Normal` 不统一洗牌。
- **当前正常容量释放**：允许合适的 `Overflow` 怪补位。若它本来就在攻击该坦克，可以原地转换为 `Normal`，无需为了产生新目标而移动。
- **容量临时升降**（装备/技能/Buff/召唤进出场）：容量增大，可增加空位；容量降低时，建议优先保留稳定已获槽位（按确定性次序），多余者转 `Overflow` 待安全时重评。不得直接删除攻击目标或中断攻击。
- **被控制、击退、沉默、死亡**：是否能够继续持有正常槽、何时释放、对行动时序的影响依照当前状态系统/已确认规则；如缺少已批准结论，**列冲突/TBD 请用户裁决**，不能为新 AI 擅自增设所有控制 Buff 的中断语义。
- **逐怪刷新与批量协调**：同一 Tick 新目标出现时，由已有 Simulation 确定性次序处理，先确认新分配、再同步预约状态，避免5只怪同时“看见空位”而全抢成功。

**不能强制平均分配**：即使野蛮人容量3、法师0、游侠0，最终法师被4只近战怪围攻也是合理结果；这为冻结/击退/召唤物/救场技能保留意义。无需按 `当前攻击者数 / 容量` 给法师/游侠算压力权重，容量0也不应作为分母。

## 6. 近战、远程、混合攻击与特殊技能

| 攻击意图 | 索敌规则 | 占用近战槽 |
|---|---|---|
| 普通近战普攻/追击 | 第3节接敌容量→临时溢出→最近合法其他目标 | 是（仅 `Normal` 持槽） |
| 远程普攻/投射物 | 最近合法目标；射程/攻击线等按现有规则 | 否 |
| 远程法师普通法术 | 最近合法目标；自身技能目标选择可单独设策略 | 否 |
| 混合怪临时切近战 | 重新按近战资格申请槽位；没有则 `Overflow` | 是 |
| 近战怪释放一次性远程特殊技能 | 技能可以临时采用自己的目标策略，**不必改变近战主锁定** | 技能不新增容量占用；原主锁定是否保留按原动作/目标合同 |
| 狙击手/刺客/后排点名 | 显式配置 TargetPolicy（最远/后排/低HP等需逐项批准） | 按具体攻击形式与配置 |
| Boss 普通近战 | 默认相同容量优先原则 | 是 |
| Boss 点名/跳跃/地面AOE | 特殊技能自己的选敌/范围，不被普通槽位强行限制 | 否（特殊技能不占额外普通槽） |

**普通远程角色并非默认“见到后排就集火后排”**。只有有明确身份的特殊怪才使用后排优先行为。远程是否后撤风筝、远程与近战切换阈值、AOE选择规则等如现有工程没有 Confirmed 合同，不在本次自动新增。

## 7. 嘲讽与主动救场拦截

- **嘲讽**：主动技能或经批准的触发效果，带目标数、效果范围、持续时长及冷却；让部分敌人进入受时限约束的 `Forced` 主锁定。技能可以临时让坦克承受超过其正常容量的近战怪；不要引入独立的“嘲讽强度/仇恨值”属性。
- **主动拦截救场**：具备有限距离的技能，可能结合跳跃/盾击/短控制/改变敌人目标；使用当前 Skill/Effect/Buff/ActionRuntime，不能绕过技能前后摇或 CD。
- **不是常驻守护**：只要怪物已绕向法师，野蛮人**不会凭借“路过”而自动重新锁定这只怪**；只有额外明确配置的技能/效果可以救场。
- **Forced 结束**：在下一合法动作边界重新执行普通选敌；若原目标有空余正常槽可以接纳，否则成为 `Overflow` 或选其他合法角色。**必须避免“3秒嘲讽结束却永久攻击坦克”**。
- **容量账本**：建议 `Normal` 预约与 `Forced` 强制锁定分别维护，`Forced` 可超过普通预约槽；实际承伤数量可能大于总正常容量。若要定义“强制锁定也占普通预约”或 Boss 免疫嘲讽，需要先核实技能/目标合同并请用户决定，不在此直接固化。
- **老技能兼容**：若已有嘲讽/控制效果，**先复用其 Effect/Buff/目标锁定接口**，不私自再写一套独立 `TauntManager`。

## 8. 召唤物、多坦、队伍动态变化

- 只要**可被正常攻击的召唤物**按配置获得非零接敌容量，便可像普通队员一样承接近战怪。骷髅战士可较少、石魔较多（测试值，不是正式数值）；不可受攻击的装饰/技能图腾不应自动成为普通合法目标。
- 召唤物有独立的战斗实例 ID；生成、死亡、回收应成对触发槽位更新与相关怪重新索敌。
- 召唤数量不能在本专项擅自加上限；由已有 Skill/Summon 规则决定。召唤物多自然会改变正常槽位总数，是 BD 成长途径之一。
- 多坦同时在场时，符合资格的坦克各自保持独立正常容量；顺序选择优先接近/可达目标，**不强行每个坦克都平均接到怪**。
- 用户已有换人“房间结束或死亡后回城找凯恩→传送回原房间继续”的玩法；本专项不得自行修改换人时点/地牢恢复/存档逻辑，须验证队员更换引起的实体/槽位清理和目标失效处理。

## 9. 入场先后与无真实物理碰撞的自然散开

**两个互相独立的系统：**

1. **逻辑**：目标锁定/接敌名额/移动至攻击距离/技能与投射物命中都以 `Game.Core` 当前权威战斗坐标与射程为准。如果仍是一维 X 轴逻辑，就继续一维 X 轴，不为了散开扩成二维寻路。
2. **表现**：为每个怪物分配与目标相关、稳定的“虚拟围攻站位”，用视觉 Y 偏移、轻微 X 避让、前后景深和动作方向实现自然散开。**视觉偏移不改变逻辑射程、投射物碰撞与伤害结果**。

建议算法（非必须命名/公式）：

- 初次锁定目标时，为该攻击者分配一个稳定的虚拟站位索引；按战斗实例 ID 稳定排序，分配同目标不同角度/纵深的表现点。
- 正常容量以内使用较接近目标的围攻位置；超额敌人可采用外圈/交错纵深的位置；**不得因为没有物理坑位而不允许攻击**。
- 当目标移动/死亡/目标锁定变化时，重新分配合适视觉锚点并做短距离平滑过渡；**不能每帧根据近邻排斥力随机重排**。
- 支持怪物视觉模型局部重叠、穿越；通过表现序和不同轻微偏移避免大量同像素完全重叠即可。必要时允许交错穿过彼此，但不要把它当作逻辑穿透/击中规则。
- 进门时**不用等整个队伍排齐**：前排有推进倾向、远程有保持射程倾向；怪物立即对已进入的合法单位作出反应，后入者触发超额重评。原有队伍移动/入门动作若已实现，最小修改其目标资格切换事件，不另建第二套门口排队 AI。

**明确排除**：`RigidBody2D` 单位推挤、单位间 NavMesh 动态障碍、刚体冲撞引发的锁敌结算、依靠肉身卡门口承担全部坦克功能。

**不能删除的旧系统**：投射物一维连续扫掠碰撞、伤害命中资格、技能范围、地牢墙体/有效区域逻辑。这里的“无物理碰撞”**只指战斗单位之间不靠真实物理推挤实现目标分配**。

## 10. 分阶段更新与数据一致性

> 以下是建议阶段职责，不声明项目现行 Tick 精确调度已如此实现；如存在已确认同刻排序冲突，按审计门禁申请决策。

```text
Tick 开始 / 复用现有输入与实体状态快照
  ├─ 收集本 Tick 的队员入场、召唤生成/消失、死亡、技能强制锁定等事实
  ├─ 对已失效目标清理引用、释放普通接敌预约
  ├─ 汇总需要新目标/超额重评的攻击者
  ├─ 在现有合法 AI 决策边界按稳定顺序计算候选并原子预占正常名额
  ├─ 产出目标/动作意图；实际动作合法性由 Action/SkillRuntime 最终判定
  ├─ Movement/Skill/Damage 按现有固定 Tick 流程执行
  └─ 输出可界定的诊断事实与视觉目标/站位指示
```

### 核心不变量

1. 每个普通近战怪物**最多持有一个** `Normal` 预约；同一目标的正常预约数不超过**当前被批准**的容量（容量突然降低时在合法边界完成有界修正）。
2. `Overflow`、`Forced` 可以合法攻击，但不凭空占用多个普通槽位；后排容量0照样可以被攻击。
3. 清理怪物、目标死亡、切房间时没有悬空预约；相同实体 ID 不因复用而指向新对象。
4. 输入/种子/配置/排序一致时，Core 无头模拟结果一致；不能依赖 Godot FPS、物理帧或 HashMap 非稳定迭代次序。
5. 普通 `Normal` 不因后排出现或 DPS 突然高伤自行换目标；`Overflow` 只在适当事件边界重评。
6. 没有接敌名额不能导致 AI 停机、延后激活、无效等待；无坦/单人可战斗。
7. 不修改 DMG1/DMG2/DMG3、Buff生命周期、Skill Commit/CD、已批准的怪物掉箱和角色奖励事实。

## 11. 可观测性、数值样例与验收效果

推荐 Debug HUD（开发模式）：当前怪物目标线；普通近战 `N`、溢出 `O`、强制 `F` 标记；各队员 `NormalOccupied / Capacity`；怪物 `TargetId / TargetReason / LastReevalReason`；入场事件和 AI 安全决策延迟。长期挂机日志必须有界。

推荐初始**测试**场景：野蛮人容量3、法师0、游侠0、8只近战：野蛮人先入场时3 N +5 O；两名后排随后进入时，N不动，O逐步选最近有效后排，后排可以被多怪围攻；没有“必须一人分一只”的规定。把坦克容量提高到5后，通常应有更多近战怪稳定承接在前排，**但具体最终数不保证等于理论容量**（会受距离/召唤/可达/其他前排影响）。

**设计确认 ≠ 已通过实机**。需要 Godot 截图/视频观察：是否马上交战，前排接敌是否可感知，后排漏怪是否自然，视觉散开是否不抖动，是否没有穿模造成的明显违和感，以及无单位物理碰撞不破坏攻击与投射物命中。
