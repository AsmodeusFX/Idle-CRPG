# Steam D2 空间配置与显示比例审计

日期：2026-10-23。范围：当前真实工程与正式配置。仅审计，不修改游戏代码、配置或玩家进度。

单位：U为地牢逻辑坐标单位；px为1440×900基准画布像素。世界区域坐标、城镇局部坐标分别说明，不假定物理尺度一致。

关键结论：战斗逻辑使用二维坐标和欧氏距离；显示是手工二维等距投影，没有Camera3D。实际生成器没有独立精英房类型，楼层规划预算不能当作运行时房间与怪物数量。

拓扑：随机选择已有房间，再选择上下左右一个空网格扩展，仅连接此次父房间。因此连接关系为树，走廊数=房间数−1。最深房间、深度并列时ID最大者标记为楼梯/Boss房。整层没有固定行列外框，包围尺寸随拓扑变化。

房间长宽独立随机，各类房共用尺寸。旧档Room缺少尺寸时字段默认7×7，不代表当前新生成尺寸。

## B. 房间类型、面积与刷新

| 类型 | 实际尺寸 | 战斗移动矩形参考面积 | 初始怪物数 | 刷新 |
|---|---|---|---|---|
| 起始安全房 | W=6～9，H=5～8 | (W−0.6)(H−0.6) | 0 | 入层建立安全房 |
| 普通房 | 同上，独立随机长宽 | 同上 | 1～5 | 首次揭示一次性生成 |
| 精英房 | 无独立运行时类型 | 无独立值 | 无独立规则 | 仅规划CSV含精英预算 |
| 楼梯/Boss标记房 | 与普通房共用 | 同上 | 总数仍1～5 | 满足Boss条件时最后名额替换为Boss |

所有房型共用门点与门框规则，没有独立逻辑门宽。

| 面积口径 | 公式 | 当前范围U² |
|---|---|---:|
| 房间地面 | WH | 30～72 |
| 普通战斗移动夹取矩形 | (W−0.6)(H−0.6) | 23.76～62.16 |
| 初始刷怪矩形 | (W−1.6)(H−1.6) | 14.96～47.36 |

没有真实单位碰撞，面积不是人数容量上限。出生与技能位移也有各自边界处理，不能把普通移动夹取矩形理解为统一导航多边形。

```text
数量 = Random.Next(1 + MinBonus, 5 + MaxBonus + 1)
数量 = Clamp(数量 + GM数量增量, 1, 1000)
位置X = 中心X + Uniform(-1,1) × (W/2 − 0.8)
位置Y = 中心Y + Uniform(-1,1) × (H/2 − 0.8)
```

来源：config/monster/spawn_rule.csv、GameSession.Reveal。

- 不按队伍人数、房间面积自动改变数量。楼层/难度主要影响等级。
- 正式楼层表的规划击杀预算、精英格数、波次字段不直接驱动当前通用每房生成。
- 无出生最小间距、去重、门口禁生区或远近程分区。
- 正式基础怪物为洞穴鼠和地牢守卫，均近战，随机选择模板。
- Boss占总数一个名额，不额外加一个；无独立随从数量和房间尺寸。
- 正常初始上限5；增量/GM可提高，安全上限1000。
- 敌方召唤另有有限槽位机制，不能把其上限混同为所有正式房间规则。
- 回访不刷新，无通用分波生成。结构在进副本前生成，怪物在首次揭示房间时快照生成。

规划与实际分离见Scripts/Core/FloorPlanning.cs；FloorReports分别记录PlannedCells、GeneratedRooms、PlannedKills、ActualSpawned等。

## C. 摄像机投影与角色显示

```text
屏幕X = originX + (世界X − 世界Y) × zoom
屏幕Y = originY + (世界X + 世界Y) × zoom × 0.5
逻辑距离 = sqrt(dx² + dy²)
```

来源Scripts/UI/Main.cs的Project。地面两轴与屏幕水平线分别约±26.565°。这是二维平行投影，无实际3D旋转、俯仰、距离或正交Size。

```text
地牢zoom = min(62, 930/(W+H), 816/(W+H))
         = min(62, 816/(W+H))
地面投影包围框宽 = (W+H)×zoom
地面投影包围框高 = (W+H)×zoom×0.5
地面投影面积 = W×H×zoom²
```

来源Scripts/UI/SceneCanvas.cs。当前zoom约48～62，多数房间适配后包围框约816×408px。房间变大通常导致缩小镜头，而不是等比例增加屏幕战斗空间。战斗固定房间中心，赶路跟随领队；中心和缩放临界阻尼过渡，入房响应5、跟随响应8，见config/system/camera.csv。预览打开时另乘0.55。

| 显示区域 | 当前规格 |
|---|---|
| 基准画布 | 1440×900 |
| 最小窗口 | 800×500 |
| 缩放模式 | canvas_items |
| 游戏场景裁切 | (24,92)，1040×558 |
| 右侧面板 | (1080,92)，336×558 |
| 底部状态区 | Y=662开始 |
| 后墙显示高度 | 固定24px |

来源project.godot、SceneCanvas.cs、HudLayout.cs。

没有统一实体碰撞半径。config/skill/runtime.csv的collision_radius=0.3U用于弹道命中，不用于单位互推或出生间距。

英雄、普通怪物、召唤物共用Scripts/UI/FollowScene.cs的DrawFighter：

```text
显示倍率s = Clamp(zoom/50, 0.8, 1.25)
Boss再乘1.3
```

- 身体主轮廓约21s宽、36s高，武器另向外延伸；阴影半径10s。
- 血条34s×4s，位于脚点上方约46s。
- 名字字体12px，锚点在上方53s，宽随文字长度变化，无固定占用框或避让。
- 当前地牢普通单位s约0.96～1.24，血条宽约32.6～42.2px。
- 友方持续屏幕Y偏移为lane×8px，英雄五人时0、−8、+8、−16、+16，召唤物继续编号；不影响真实坐标。
- 怪物接敌绘制偏移约X方向18～24、Y方向13～22px乘接近系数，方向依稳定实例ID变化。来源MotionPresentation.cs。

## D. 拥堵截图的数据边界

本轮未附对应截图或存档；当前正式配置和文档未检索到“黑洞匪窟”。不能擅自对应为“邪恶洞窟”，不能仅凭“第1层、第1/8房”或“第1/11层、第3/8房”反推种子、POI和现场坐标。

- 8房符合每层6～9房范围；11层可能来自POI覆盖，但不能据此确定具体副本。
- 若第1/8房指内部Room.Id=0，应为安全起始房；若为清理计数，则不能这样解读。
- 精确W/H、实际怪物数、英雄/召唤数、平均最近邻距离、首次接战位置均无法由标签唯一确定。
- 早前summon-d2截图为隔离QA，改过怪物HP和位置，不能代替用户截图房间的自然生成数据。

可确认的配置范围及密度计算：

```text
移动参考面积A = 23.76～62.16 U²
基础敌人数 = 1～5
实际单位总数N = 房内英雄数 + 活召唤数 + 活怪物数
面积分摊特征长度 = sqrt(A/N)
实际平均最近邻距离 = sum_i(min_{j!=i}(distance(i,j))) / N
```

sqrt(A/N)仅为密度尺度，不是实际间距。无碰撞时实际最近邻距离可趋近0。

从代码可确认的拥堵因素：门线内即交接战斗、进入射程即停止、怪物启动后向入口候选追击，叠加全房固定镜头和不避让的名字/血条。具体主次需对应现场数据，当前不伪造运行测量。

## E. 参数关联

| 关联项 | 影响 |
|---|---|
| 房间尺寸与12U网格间隔 | 同时影响走廊净长，不能无限放大 |
| 房间尺寸与自动镜头 | 尺寸增大通常使zoom下降 |
| zoom与角色尺寸上下限 | 角色不与地面严格同比缩放 |
| 房间尺寸与0.8留白 | 共同决定刷怪矩形 |
| 移速、射程、警觉时间 | 共同决定首次接触位置 |
| 数量、召唤数、名字宽度 | 共同影响屏幕遮挡 |
| 入场交接条件与射程 | 决定是否刚入房便停止 |
| 世界比例与城镇局部比例 | 共用投影但不是同一逻辑速度尺度 |

纯表现项：屏幕接敌偏移、角色几何、名字/血条、墙高、门框像素尺寸、镜头平滑。它们不增加逻辑通行面积。

## F. 缺失配置与代码常量

没有独立配置的项目：普通/精英/Boss房尺寸和逻辑门宽；实体占地半径；出生/同阵营最小间距；门口禁生范围；远程出生分区；按面积分配实际怪物数；入场通行带深度；全队进入进度对应敌方启动条件；名字和血条避让。

当前代码常量包括：网格步长12、走廊绘制半宽0.65、门触发0.32、出生内缩0.4、战斗边缘0.3、部署边缘0.4、刷怪边缘0.8、门框20×29px、墙高24px、镜头适配宽930、地牢纵向留白150、城镇留白100、角色几何及倍率上下限、友方车道8px、怪物数量安全上限1000。
