### 2.2 明确四个不应混用的数值

- `MonsterLevel`：进入具体战斗实体的怪物等级，驱动怪物属性/经验/掉落资格的后续计算。
- `FloorMonsterLevel`：一层地牢的常规怪物配置等级，可由 `Difficulty×Chapter` 默认值及 POI 局部偏移得到。
- `DungeonChallengeLevel`：**整座地下城用于自动排程的难度标签**；不必等于第一层怪物等级，可建议取最后几层或最高核心遭遇等级，但**推导公式未批准**，首版可直接配置独立整数。
- `RecommendedPlayerLevel`：建议小队主力角色等级，不是解锁硬门槛；建议与 `DungeonChallengeLevel` 独立配置，避免未来技能和装备改变难度而误伤排序。

**强制约束**：自动选择器只能读取显式配置/解析后的 `DungeonChallengeLevel`，不得用地图面积、最近格、关卡 UI 排名或玩家当前等级偷偷重写优先级。

## 3. 全自动攻略：数据、状态和选择规则

### 3.1 世界级状态

```
Chapter / Difficulty
  └── Region (Unlocked, Conquered)
       ├── Dungeon POI × N  → DungeonFloors (1..N)
       └── Castle POI       → CastleFloors  (1..M) → CastleBoss
```

**永久进度事实**（按 `DifficultyId + ChapterId + PoiId` 等复合键保存）：

- `DungeonFirstCleared`：这座地牢的**全部规定楼层**及其终点条件完成。
- `CastleConquered`：该 Castle **内部挑战及 Boss 胜利**已正式提交。
- `ChapterMainCleared`：最终 Castle 完成后派生/写入的主线完成事实；Act 1 **不要求血乌支线**被征服。

**派生状态**（不建议作为互相独立的权威布尔值存档）：

- `RegionUnlocked`：满足前置 Castle 依赖；
- `CastleEligible`：本区域 `RequiredForCastle=true` 的**独立地牢入口**都首次通关；
- `PoiReachable`：大地图存在合法路径（4 邻接 + Gate + 解锁许可）；
- `ExpeditionCandidate`：已解锁、可达、未通关，且其特定前置/资源合法。

地牢的**一次临时战斗实例**、当前 Floor 进度、随机种子和死亡重试，不等同于永久首次通关事实。

### 3.2 候选列表和稳定排序（已确认规则）

`EligibleTargets = { p | RegionUnlocked(p) AND Reachable(p) AND NotFirstCleared(p) AND PoiPrerequisitesMet(p) }`

- Dungeon：区域已解锁，入口有效，未首通，可成为候选；
- Castle：除通用条件外，还需 `CastleEligible=true`；
- 章节最终 Castle：完成真实 Boss/全部必要 Floor 后才产出 `ChapterMainCleared`；
- 已通关 Dungeon / Castle **不进入未通关候选集**；它们可以进入将来独立定义的“回刷候选集”，不可两者混淆。

排序键（递增，左边优先）：

```
(
  DungeonChallengeLevel,
  BranchPriority,       // Main = 0, Optional = 1（同等级时）
  AutoOrder,            // 设计表显式整数；固定稳定
  ChapterOrder,
  RegionOrder,
  PoiId                 // 最终确定性兜底
)
```

`BranchPriority` 只用于 **挑战等级相同** 的情况；**不得以“支线”身份压过等级更低的目标**。因此血乌支线可被小队自动先打，但不阻断石块旷野推进。推荐玩家等级只用于说明/预警，不改变已批准的排序。

> 【待定，需要单独确认】：`EligibleTargets` 的“当前攻略范围”是否允许跨已开放的不同章节/难度进行全局排序；建议第一版在**当前激活难度的已开放章节集合**内排序，并将攻略范围作为可配置策略，不把该建议冒充已批准规则。跨难度自动切换时机另行审批。

### 3.3 自动流程状态机（建议命名）

```text
LoadAndValidateConfig
      ↓
ResolveProgressAndUnlockedRegions
      ↓
BuildEligibleTargets → StableSort → ChooseFirst
      ↓                       └─ 无目标 → Idling / EndOfScope (不得虚构通关)
BuildTravelPath (Grid + Gate)
      ↓
AutoTravelOnWorldMap (无战斗)
      ↓
EnterDungeonOrCastle
      ↓
GenerateFloor(Seed, FloorProfile)
      ↓
TeamExploreAndFight → CheckFloorClearCondition
      ↓
If more floors: FloorTransition → GenerateNextFloor
Else: CommitPoiClear / CastleConquered
      ↓
UpdatePermanentProgress → RecomputeUnlockGraph → Save
      ↓
BuildEligibleTargets ...
```

建议把导航与战斗完全分开：`AutoExpeditionCoordinator` / `TargetSelector` / `TravelPlanner` / `DungeonRunCoordinator` / `ProgressStore`（**概念名，不要求实际类名相同**）。

### 3.4 必须面对的异常路径

- 路径不存在 / Gate 不合法：候选必须剔除或报配置错误，不允许“瞬移过去”掩盖错误。
- 入口内容缺失：标记 `BLOCKED / NOT IMPLEMENTED`，不可假装已完成继续解锁；需避免自动重试形成死循环。
- 战斗失败：产出独立 `RunFailed` 事实，但**不得将其当成永久地牢完成**。回刷重试策略 TBD，需可插拔。
- 结算原子性：只有有效 `FloorComplete` 才切到下一层；只有完整 Dungeon / Castle 成功完成才写永久首通。已经提交的击杀/宝箱/奖励不被失败或路径重试回滚。
- Godot UI 不能自己决定解锁和通关；Battle/Core 事实驱动地图进度。存档恢复后，重新由配置和事实计算派生状态。

### 3.5 分支与自动攻略示例（Act 1）

- 罗格营地 → 鲜血荒地 → 冰冷之原；
- 冰冷之原 Castle 真正被征服后，**埋骨之地、石块旷野同时解锁**；
- 系统从两区所有合法未清 POI 中取最低 `DungeonChallengeLevel` 的目标；同级时主线优先；
- 埋骨之地完成与否**不影响**石块旷野及其后继解锁；
- 黑色荒地 **遗忘高塔 = Castle 本体**，女伯爵/高塔地下室不额外作为前置 Dungeon；
- 修道院 **大教堂 = 最终 Castle**，地下墓穴是 Castle 内部深层，不计入该 Castle 的前置 Dungeon，终点是安达利尔。

## 4. 地牢格子：必须先统一计量单位

**不要把三个层级的“格子”混在一起：**

| 层级 | 建议数据名 | 代表什么 | 是否直接用于怪物预算 |
|---|---|---|---|
| **章节大地图地块** | `WorldTile` | Act 1 的 8×8 地形与 POI 位置 | **否**；一个入口可以连接多个 Floor |
| **地牢生成网格格子** | `DungeonCell` | 一层地牢的**一个房间/走廊段/节点**；是规划单位，不等于人物脚下一块 TileMap 像素格 | **有条件**；取决于格子类型 |
| **战斗导航 Tile / 世界距离** | `NavTile`、`WorldUnit` | 实际 2D 移动、碰撞、索敌的精细网格与单位距离 | 否，服务局部实际 AI / 场景物理 |

**每层应同时配置：**

1. `LayoutRows / LayoutCols`：容纳布局的包围矩形大小（仅控制大致布局形态）。
2. `ActiveCellCount`：实际连通、生成的地牢逻辑格数（包含入口、走廊和战斗房间）。
3. `CombatCellCount`：其中**允许按标准怪物预算生成怪物**的普通战斗格数。
4. `SpecialCellCount` 与 `SpecialEncounterRefs`：精英格、事件格及 Boss Arena；不能简单按普通战斗格倍乘。
5. `CellKind`：推荐 `Entry / Corridor / Combat / Elite / Event / Exit / BossArena`，一格同一时刻应具有明确的主生成用途。
6. `SpawnProfile`：不同 CellKind 的怪物预算和怪物池；设计数量是**规划预算**，真正生成由配置/种子驱动。

必须满足：`ActiveCellCount ≤ LayoutRows×LayoutCols`；`CombatCellCount ≤ ActiveCellCount`；所有生成可通行格在约束下连通，入口可达终点；Boss Arena 一般由**连续若干格组成同一个战斗场地**（不是每格各生成一个 Boss）。

### 4.1 每层规模档位（设计建议，未批准）

下面的格数是**逻辑房间/走廊段**，**不是 D2 原版的地图像素或精确 Tile 数值**。目的是保留“邪恶洞窟短小、女伯爵逐层深入、终局要塞明显宽阔”的**主观空间感**。

| 档位 | 活动格数/层 `ActiveCellCount` | 格局建议 | 适用内容 |
|---|---:|---|---|
| XS · 极短 | **8–12** | 入口 → 小岔路 → 少量战斗房 | 鲜血荒地新手洞穴、短支线 |
| S · 短 | **12–18** | 少量支路，战斗不密集 | 一般洞窟、早期地牢 |
| M · 标准 | **18–28** | 主通路 + 1–3 支岔 | 普通中期地下城 |
| L · 深入 | **28–42** | 多房间、明显回路 / 精英节点 | 高级地牢、Castle 主体楼层 |
| XL · 大型 | **42–60** | 大厅、分段回路、长廊、Boss 前厅 | 特殊终局层、大型要塞，**不应每层都最大** |

档位**不等于每层必须有这么多战斗房间**。尤其走廊、空地、入口、过场可以占较多格；让玩家可以看见“在探索”，但总空跑时间仍应受限。**整章规模同时由入口数量、层数、活动格数和刷怪格密度决定**，不能只靠增加楼层拖长时长。

### 4.2 每格怪物密度（设计建议，未批准）

| CellKind | 首版建议初始在场怪物数 | 说明 |
|---|---:|---|
| Entry | 0 | 出生安全与角色集结，不默认刷怪 |
| Corridor | 0–1 | 主要为连接与节奏缓冲；可以有轻量遭遇 |
| Combat | **2–4** | 普通遭遇组；按区域怪物池及预算生成 |
| Elite | **1 精英 + 2–4 随从** | 单独按精英编队计数，**不再叠加普通 Combat 配额** |
| Event | 0 或单独配置 | 机关/事件/宝箱等非默认怪物内容 |
| Exit | 0–1 | 楼层出口；是否设置守卫由配置决定 |
| BossArena | **1 Boss + 0–6 随从（整座 Arena 合计）** | **按遭遇组计一次**，不可对 Arena 每个格子执行一次刷 Boss |

**密度扩张建议**：后期增加怪群或波次时，可调整 Combat 组的 `SpawnCount`，但不应简单把每格数随等级无限翻倍；真实同屏怪物上限、怪物碰撞与 3–5 人小队的演出遮挡需要 Godot 测试后才批准。

### 4.3 Boss 房间必须被当作专门内容类型（设计建议）

- BossArena 应具有**独立房间模板**、预留入口和站位、明确的开战触发与完成条件；不能把 1 只 Boss 塞进普通 1 格走廊。
- 中小型精英 Boss：可由 2–4 连通逻辑格组合成一个 Arena；章节终局 Boss：建议 4–8 个连通逻辑格组合，整体仅作为**一次 Boss 遭遇**。
- 允许终局层 `BossArena` 占面积较大，但**降低普通怪物密度**；Boss 面积与怪物数量不能一起简单叠加，避免 3–5 人小队不可读。
- 可以配置 `BossIntro`、`Phases`、`Summon/WaveBudget`、`ExitAfterBoss`；数值与动画尚待制作。虚拟层数或“多个走廊段”不等价于独立 Boss 战。
- 内部 Castle 的中间层可以是走廊＋营房＋大厅，最后层则应围绕 Boss 场景设计；**Castle 的广阔感可以来自更大的房间、更长的路径，不只来自更多怪物。**

## 5. 怪物数量和预计击杀模型

### 5.1 分清四种数字

- `InitialSpawnCount`：楼层初始生成的所有怪物实体数。
- `ScriptedAdditionalSpawnCount`：脚本/波次**确实额外生成**的怪物数；若全部会被玩家击杀才能通关，才可计入必杀预算。
- `PlannedKillCount`：设计预期需要实际击杀的怪物数量，服务章节时长、掉落次数与效率建模；不是纯粹“刷怪次数”的同义词。
- `ActualKillFactCount`：战斗运行中真正提交的有效击杀事实数量，供奖励统计；**不得由设计预算直接发奖励**。

为支持数据建模，还建议区分 `RequiredKillCount`（完成关卡必须击杀的最小数）、`ExpectedKillCount`（自动探索后的预期击杀数）和 `MaxPlannedSpawnCount`（生成上限，不含 Boss 动态未控召唤）。

### 5.2 粗估公式（可直接用于配置表统计）

对于 Floor `f`：

```
BaseKills(f)
  = Σ_{cell in generated/fixed cells} InitialMonsters(cell)

PlannedKills(f)
  = BaseKills(f)
  + ScriptedAdditionalMonsters(f)
  - OptionalMonstersExpectedToRemainAlive(f)

DungeonPlannedKills(d)
  = Σ_{f in floors(d)} PlannedKills(f)

ActPlannedKills(act, difficulty)
  = Σ_{mandatory Dungeon & Castle first clears} DungeonPlannedKills(d)
  + Σ_{optional Dungeon & Castle first clears actually scheduled} DungeonPlannedKills(d)
```

说明：上述公式的**脚本增援只能计算新产生的独立怪物实体**；同一批怪物在延迟刷新界面时不能重复计。为避免“必杀数量”误差，建议从独立的 `SpawnEncounter` 定义聚合，而不是单靠 `CellKind` × 统一密度常量。未清完所有怪物也能通关的关卡，要扣除预期未杀的可选敌人。

**敌人召唤/复活的特殊问题**：若召唤物、复活怪会贡献 KillFact，必须独立定义 `CountsTowardProgress`、`CountsTowardLoot`、`CountsTowardStats`、`SpawnLineage`；不能因为同一 Boss 无限召唤小怪，就让章节击杀和宝箱产出无限膨胀。这里是后续设计红线，具体计数规则仍 TBD。

### 5.3 用三个 D2 情怀锚点举例（全为预估，不是原版实测）

| 内容 | 楼层规划建议 | 单层活动格数 | 布怪假设 | 粗估击杀量 | 要验证的感受 |
|---|---|---|---|---:|---|
| **邪恶洞窟**（鲜血荒地） | 1 层 | **10** | 5 普通战斗格×3 怪 + 1 精英×(1+2 随从)；其他为空或连通格 | **18** | **小而快**，开局尽快过关，同时有短暂搜索/清怪过程 |
| **遗忘高塔**（黑色荒地 Castle） | **5 层** | 每层约 **14 / 16 / 18 / 20 / 24** | 分层增加战斗格和精英；末层女伯爵 1 Boss 与护卫组 | **约 110–175**（总计） | **深入五层**，越深越有压力；不需要每层都巨大 |
| **大教堂 → 地下墓穴**（修道院 Castle） | **1 层大教堂 + 4 层地下墓穴，合计 5 层** | 每层约 **26 / 28 / 32 / 36 / 40** | 大厅、长廊、精英组；最终安达利尔专用 4–8 格 Boss Arena，Boss 只计 1 次 | **约 250–390**（总计） | 前段逐步深入，最后 **Arena 宽阔、单场 Boss 演出突出** |

> **口径提示**：这里的 `10` / `14–40` 指地牢抽象的逻辑格数，不是 D2 贴图 Tiles、也不是生成器必须恰好用这些布局。`遗忘高塔 5 层` 与 `地下墓穴 4 层` 是为了保留经典深度的**优先建议**，具体 Floor 内容须 Chapter 1 V0.5 再逐层配置。邪恶洞窟的清怪目标建议接近 D2 的“清掉所有邪恶怪物”，但是否要求全清、回头搜残怪和自动补漏策略仍待专门确定。

### 5.4 估计战斗时长时必须加入移动与技能节奏

`ExpectedDuration ≈ Σ[ExpectedKills / EffectiveKillsPerSecond] + Σ[TraversalTime] + BossFightTime + FloorTransitionTime`。

这里 **KPS 是实测有效击杀速率**，不能单纯按理论 DPS / 单怪 HP 获得；小队的自动索敌、敌人聚集、走廊宽度、远近程攻击、死亡后转向都可能改变实际效率。推荐玩家等级、怪物等级相同，也不等于同样的 KPS。

**提供报表字段**：每层 `ExpectedKills`、`ActualKills`、`KillDelta`、`CombatTime`、`TravelTime`、`TransitionTime`、`Deaths`、`AttemptNo`、`Seed`、`ChallengeLevel`、`DifficultyId`。后期可用于拟合实际时长、经验产出、普通/稀有/炫彩宝箱期望收益与装备成长曲线。

### 6.1 `FloorProfile` JSON 示意（完全虚构，用于校验字段）

```json
{
  "dungeonDefId": "A01-D01",
  "difficultyId": "NORMAL",
  "floorIndex": 1,
  "layoutRows": 3,
  "layoutCols": 4,
  "activeCellCount": 10,
  "cellsByKind": {
    "Entry": 1,
    "Corridor": 2,
    "Combat": 5,
    "Elite": 1,
    "Exit": 1
  },
  "spawnProfiles": {
    "Combat": { "min": 3, "max": 3 },
    "Elite": { "elite": 1, "minions": 2 }
  },
  "completionCondition": "ALL_REQUIRED_ENEMIES_DEFEATED",
  "plannedKillCount": 18,
  "bossArenaRef": null
}
```

**该示例的验证关系**：`1+2+5+1+1=10` 个活动格；`5×3+(1+2)=18` 个规划击杀。`layoutRows×layoutCols=12` 允许有 2 个不生成/不可走格。**当前 JSON 仅示意配置内容，不要求 Claude Code 原样照搬序列化字段与类型。**

### 6.2 强类型校验与安全边界

1. `DungeonDefId + DifficultyId + FloorIndex` 唯一；`FloorIndex` 从 1 连续到 `FloorCount`；Castle 内多层不能重复作为前置 Dungeon POI。
2. `0 < ActiveCellMin ≤ ActiveCellMax ≤ LayoutRows×LayoutCols`；`0 ≤ CombatCellMin ≤ CombatCellMax ≤ ActiveCellMax`。
3. 生成后 `Σ CellKindCounts = GeneratedActiveCells`；所有可走格连通、入口到出口/Boss Arena 有合法路径；大地图 `WorldTile` 不应混入该统计。
4. 对 Elite / Boss：如多格 Arena，则按**EncounterId 唯一生成一次**；禁止每格重复生成 Boss，禁止把同一个随从队列同时记为 Combat 和 Boss 配额。
5. 生成器的 `SpawnBudget` 不应超出关卡上限；所有怪物生成池合法；Boss 战的胜利条件不允许仅靠杀普通随从误触发。
6. `PlannedKillCount` 可以从确定性布局/遭遇表自动聚合，不能作为绕开战斗的完成凭证或直接生成开箱奖励。
7. 随机种子、配置版本、层次与生成结果应可复现；存档/恢复不能因重新投种而凭空补怪或重刷已提交的 KillFact。
8. 异常/缺失 Floor 配置应报 `BLOCKED/CONFIG_ERROR`，不得自动将目标视为已通关；对无解区域解锁、Gate 断联、必清循环前置给出显式诊断。
