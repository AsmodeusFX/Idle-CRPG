# Steam D2《暗黑放置》｜P2-3-M5 首轮 UI/UE 交互规格 V0.2

> 2026-10-25 · `[C]`既定原则＋`[P]`建议布局/优先级 · **设计稿，非Godot实机效果/实现授权**。
> M4工程现状：单窗口 `Main.tscn`，当前设计尺寸1440×900，已有“游戏/英雄/星图/地图”页签；右侧仅城堡与编队卡，缺英雄升级、装备与资源操作；Godot实时画面尚未提供。

## 1. 信息架构与主要操作闭环

**不改变已经确定的单窗口结构。** 保留战斗作为主视觉，已有四页签作为可复用入口。新增能力优先复用页面和右侧行动区，而非发明Mini/Management双窗口。当前尺寸只是工程基线，最终窗口缩放与响应细节由执行AI依据Godot取证适配，设计Owner验收遮挡与可读性。

```text
[游戏页/战斗中心] → [右侧：可处理事项] → [英雄页/指定角色升级或天赋]
          │               ├→ [装备详情：本次将替换的角色/部位/属性]
          │               ├→ [KP面板：怪级区间／费用／资格]
          │               ├→ [星图页：本轮金币购买]
          │               └→ [城堡：门槛／独立挑战]
          └→ [卷轴快捷入口/药剂槽：战中手动使用]
[开局] → 选1～4英雄/允许重复职业 → 锁定本轮 → 以上循环
[首轮第四章] → 确认重生 → Run清零、Account保留 → 新轮选队
```

推荐游戏页呈现信息：战斗区域优先；XP池/KP/金币和当前`[Lmin,Lmax]`轻量可见；右侧只显示动作摘要、足够的代价/收益预览及状态。点击进入详情才展示复杂的角色或物品清单。


### 1.1 游戏页结构线框（仅内容层级示意，不锁像素）

```text
┌────────────────────────────────────────────────────────────────────┐

├────────────────────────────────────────────┬───────────────────────┤
│                                            │ 成长与待处理            │
```

标号只表示草案优先级，不是已批准的完整排序。右侧动作过多时采用折叠列表/分组，不以无限高度叠加遮挡战斗。玩家进入“英雄”等详情页后，回到游戏页应保持战斗运行和资源生产；除明确的用户确认动作外，不因打开界面而自动增强角色。

## 2. 右侧成长队列——确认与建议分离

| 操作组 | 显示内容 | 执行行为 | 禁止的行为 | 标记 |
|---|---|---|---|---|
| 英雄升级 | 实例名/职业/当前级→下级、费用、XP池余额、升级后的主要变化 | 玩家**指定英雄，每点击一次只升级一级**；消费公共XP | 全队一键升级、自动连升、离线/回城自动分配 | [C] |
| 装备替换 | 可更换部位总数、角色实例和部位、换前/换后主属性 | 单部位逐件可点；达到**5个不同可换部位**显示“批量替换N部位”，展开清单，一次点击执行所列有效替换 | 自动穿戴、将同一部位多候选算多件、回城先售卖更好候选 | [C]+[P]去重 |
| KP购买 | KP余额、购买费用、升级前/后怪级区间、全员AR/DR门槛、风险提示 | 一项选择单次确认，扣KP更新Run | 合并多项购买、用队伍平均评级代替所有上阵者、无验收开放Lmin | [C] |
| 城堡挑战 | 所需Lmax门槛、当前区间、章节状态、可挑战原因 | 玩家明确点击挑战 | 自动攻城、把城堡决定合并KP购买 | [C]；门槛细则[O] |
| 天赋/星图 | 尚有点数／当前能买的节点、点击后的变化 | 玩家主动进入对应页面分配/购买 | 自动分点或花金币、星图出售技能槽/普通席 | [C] |
| 卷轴/药剂 | 数量／槽位／持续时间与状态 | 玩家直接主动使用；后期自动卷轴能力由星图解锁 | 无限免费自动施放、药剂使用后立即腾槽 | [C] |

**队列排序建议[P]**：英雄升级固定置顶；其次可换装备、KP提醒、天赋/星图、城堡可挑战。危急或失效提示可作为顶层小提示，但不得替玩家执行。卷轴/药剂更适合战斗快捷入口，不依赖右侧队列排序。该排序需用户裁决或先以原型展示再验收，不视为当前已批准设计。

### 2.1 装备批量换装的定义与事务

- `可换部位`唯一键为 `(HeroInstanceID, EquipmentSlot)`。当前若同部位有多件候选，仅展示确定的本次最佳候选；可选次优需去详情页，不得默认误替。
- 原型装备每件先允许一条主属性，以避免ATK+HP交叉比较的隐式自动决定；出现不可客观比较的多属性时只显示对比，不能静默批量穿上。
- 点击前展示“野蛮人#1：武器 20→25；法师#2：胸甲 HP100→120”等列表。按钮文案`批量替换5件装备`，如只有3个不同部位则以3张独立换装项呈现。
- 点击执行时重新检查装备仍在、角色ID匹配、部位合法、候选仍优于当前；采用一次事务更新并刷新待办。处理过期/失效项必须有明确反馈，不因重复点击产生复制道具。
- **先保留待换候选，再卖掉无用杂物/旧货**；出售只能影响已明确判定为可卖的物品，不能因背包满而清掉可换候选。

## 3. 独立UI任务与状态矩阵

| UI-ID | 页面/流程 | 必验状态 | 用户可观察的成功反馈 | 边界/失败态 |
|---|---|---|---|---|
| UX01 | 开局组队 | 1–4人、重复职业、角色实例区分、点击确认锁队 | 已选人数/职业清单/本轮锁定提示 | 0人不可开始；中途换队跳到“放弃本轮”并说明重置范围 |
| UX02 | 英雄升级 | 够XP/不足、当前级/所需XP、指定目标 | 点一次升一级且XP余额/AR/DR/天赋点可见更新 | 双击、多个英雄同时可升、重载不自动领取升级 |
| UX03 | 装备 | 0/1/4/5/大量可换部位、同职不同实例、清单展开 | 实际人物/部位/属性变化、剩余候选数 | 一件多候选、槽满、售卖前保留、重复点击 |
| UX04 | KP/Lmax | KP不足、AR或DR不足、可升级、升级成功 | 区间变化，费用/各英雄门槛展示一致 | Lmin玩家入口禁用；不可逆动作预警；旧数值不双活 |
| UX05 | 城堡 | 未达到门槛/可挑战/战斗中/成功/失败 | 章节与资源进度更新 | 用户未确认前不自动挑战；失败不误重生 |
| UX06 | 卷轴 | 无库存/有库存、有目标/无目标、战斗结束 | 释放效果及库存减少一次 | 无目标不扣库存，避免无限循环自动使用 |
| UX07 | 药剂 | 空槽/待用/使用中/到期、槽满 | 计时与Buff可见，使用中占槽，到期释放 | 关闭/重载时处理计时需有一致规则，不静默覆盖 |
| UX08 | 星图/天赋 | 足额/不足、互斥分支/局部洗点、重生后重置 | 点数/金币变化及效果可见 | 不出现旧技能槽、党派/普通席购买选项 |
| UX09 | 重生/放弃/全清 | 不同操作不同界面警告与确认 | 明确“保留什么／清除什么”及完成记录 | 放弃不领奖，全清应强二次确认，读档不吞账号 |
| UX10 | 单窗口/后台 | 正常/最小化/恢复/不同缩放 | UI可见、已赚资源继续累计且不自动增强 | 不因窗口失焦误触自动消费，主要战斗画面未遮挡 |

## 4. UI规格输出与交付证据

每个UI任务包必须有：`UI-ID、关联D-ID/数据命令、入口、信息/按钮/禁用逻辑、完整状态转换、样式/优先级约束、异常、存档重载、首轮数量压力`。设计Owner出文字规格/线框，用户裁决重大体验变化；执行AI可自主调整控件布局和适配，但不得悄然改变用户点击决策。

执行AI必须提交**实际Godot运行**截图/短录屏（不是生成的效果图）、运行环境、准确重现路径、窗口尺寸/缩放、主要状态至少各一例，及Core命令和最终状态核对。Review拆为：①功能与状态正确；②信息层级/可读性/交互负担；③整合回归。`dotnet build PASS`不等于三项PASS。当前Godot PATH没有命令，需在首个UI包前找到实际路径或明确具备可操作的替代实机设备；不允许只以静态截图宣称可操作。

## 5. 仍需产品或P2-5数值定案的事项

- `[O]` 城堡只看`Lmax ≥ N`（设计Owner推荐）还是需先实杀该级怪；M5需要用户关键裁决。
- `[O]` 提升Lmin的严格安全实现；P2-4默认不展示可购买入口。
- `[P]` 操作队列同级排序、原型部位数量与面板具体布局：由设计Owner提出初稿，用户可集中裁决，不应阻塞Core基础包。
- `[O]` 装备复合属性优劣比较、药剂关闭游戏后的计时规则、旧档迁移的账号价值迁移原则；各自WP开工/验收前明确。
- XP/KP/AR/DR价格/公式、药剂时长、星图节点最终价格/拓扑都是P2-5A正式数值工作，原型仅用临时标记参数。
