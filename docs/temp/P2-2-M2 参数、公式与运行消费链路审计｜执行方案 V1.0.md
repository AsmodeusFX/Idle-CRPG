# Steam D2｜P2-2-M2 参数、公式与运行消费链路审计｜执行方案 V1.0

**阶段**：P2-2「全系统配置结构盘点与扩展能力审计」／M2  
**执行对象**：Claude Code  
**前置**：P2-2-M1 `P2_2_M1_PASS`；P2-1 `M3_TEST_ENV_PASS`  
**性质**：只读审计＋必要的测试侧/导出工具补充。不是数值设计、内容生产或正式配置修改指令。

## 0. 本轮目标

把 M1 的「系统、配置、内容 ID 清单」推进为可供 P2-3 使用的**参数—公式—消费方—验证方法**设计资产。

本轮必须回答：

1. 现有正式配置中有哪些字段，分别表示什么，默认值、单位、范围、前置与覆盖优先级是什么？
2. 每个影响玩法的参数在哪里进入 Core，如何参与计算，何时生效，最终影响什么结果？
3. 现有属性 Key、Effect、天赋、星图、技能、怪物、房间事件等机制，能通过配置扩展到什么程度？
4. 哪些参数已生效，哪些仅加载、仅规划、仅预览、被覆盖、空投放或缺少消费方？
5. P2-3 设计正式内容时，哪些是纯配置工作，哪些需要**扩展现有系统**，哪些属于新增独立系统、应排除？

**特别强调**：现有属性、价格、经验和怪物数值仍是测试占位数据；不评价某系统的强弱，也不进行平衡调整。

## 1. 输入与口径校验（先做）

以真实仓库为最终依据；复用 M1 已建立的只读审计工具与下列资料：

- `docs/data/2026-10-24_00-03_data_p2_2_m1_inventory.md`
- `docs/data/system_inventory.csv`
- `docs/data/config_manifest.csv`
- `docs/data/content_registry.csv`
- `docs/data/content_expansion_gaps.csv`
- `docs/data/issues_and_decisions.csv`
- P2-1-M3 的模拟环境验收与现有 `SimulationRunner`、Core Checks。

先核对 M1 已知的记数/表述差异，以 **CSV 明细和真实代码**为准，不擅自改正式配置：

- `config_manifest.csv` 实有 **391 文件**：**195 CSV、195 `.import`、1 `.translation`**；其中正式 `ACTIVE` CSV **142**（M1 正文一处写为 141）。
- `system_inventory.csv` 实有 **31 条**，而 M1 输出清单一处写为30；正文计数与实际明细一致。
- `content_registry.csv` 实有 **4,278 条登记**。它包含规划记录（例如楼层预算），不可全称为运行时实投放。
- 天赋：61 节点，其中39主动、22被动；M1 记载24个主动无 `skill_id`，需核实正式绑定数量与个别章节的不一致表述，不沿用未经核实的“38个已绑定”说法。
- 属性：36 Key，M1 约17项未有配置投放；必须逐 Key 复核“未投放、未消费、仅有默认值”三种不同状态。

审计开始和完成时保存配置/源码指纹；若与 M1 已记录版本不同，说明变化范围并据此更新结论。

## 2. M2-A｜全量参数台账

针对全部 **142 份 ACTIVE CSV** 和它们的有效字段建立机器可读的 `parameter_registry.csv`。以 `(正式来源路径, 列名)` 为物理覆盖单位；对于五章共用 Schema 的列，可增加规范化的 `schema_group`，但不得因合并而丢失任一文件的覆盖证明。

建议字段：

| 字段 | 含义 |
|---|---|
| `parameter_id` / `source_path` / `column` / `schema_group` | 稳定参数标识、表及列、跨章共用模式 |
| `system` / `mechanism` | 归属系统和子机制 |
| `value_type` / `unit` / `semantics` | 类型、单位、确切设计含义；整数/比例/毫单位/秒/Tick等不得混写 |
| `role` | ID、外键、枚举、开关、业务数值、展示参数、规划字段等 |
| `loader` / `runtime_consumer` | 读取点、实际消费点，定位到类/方法，尽量附行号 |
| `default_and_fallback` / `override_priority` | 缺失值处理、章节/共享/角色/运行时覆盖次序 |
| `validation_and_bounds` | 校验规则、上下限、Clamp、拒绝或静默退化行为 |
| `apply_stage` / `aggregation` | 生效时点、base/flat/pct等计算方式 |
| `scope_status` / `verification_level` | ACTIVE消费、仅加载、规划、历史、无消费者；STATIC_VERIFIED/RUNTIME_VERIFIED/PENDING |
| `test_reference` / `notes` | Core Check/模拟测试及未证实事项 |

要求：

- 全部 ACTIVE 文件与字段有覆盖记录；外键、名字、展示字段等**可以标为非数值字段**，不要求伪造消费公式。
- 对运行中可能覆写的同名字段，写明**最终权威数据源**，尤其是 `dungeon.csv`、`poi_profile/poi_challenge`、正式章节与根目录 legacy 的优先级。
- 对 `checkpoint_seconds`、`spawn_planning.csv`、`floor_plan` 预算之类，明确区分「无人读取／读取但无人消费／只用于统计」；不把规划字段当作游戏逻辑。
- 记录 M1 已发现的缺表静默降级、空 Trigger/Proc 投放等风险，不在本轮修改。
- 逐字段覆盖可以由工具自动枚举，再人工复核核心链路；不得声称代码路径未经检查的字段全部已运行验证。

## 3. M2-B｜公式依赖与运行消费链

建立 `formula_dependency.csv`，按**实际代码公式和依赖**而非想象中的策划公式登记。

每条包括：`formula_id`、机制、输入 Key/配置字段、公式与运算顺序、默认值、Clamp/舍入、随机数调用、触发时机、输出状态、写入点、受影响系统、源码证据、现有检查、验证级别、风险。

重点追踪以下链路（允许按仓库事实补充）：

1. 英雄经验：怪物奖励基础值 → 等级差倍率 → 小数精度累积 → 升级门槛 → 等级/属性/天赋点。
2. 金币经济：实际掉落 → 拾取/售卖 → 星图购买/洗点支出 → 余额；保持与 M3 金币账本口径一致。
3. 战斗伤害：基础属性、属性聚合、伤害类型、护甲与抗性、暴击/格挡等 → 结算 → HP/死亡/奖励。
4. 技能/Effect：学习与上阵 → AI合法性与动作阶段 → Commit → Effect/投射物/Buff/召唤 → 伤害、治疗或持续效果。
5. 怪物：身份、行为、精英/Boss 配置、等级与难度 → 实际刷怪与战斗策略。
6. 星图：节点布局与前置 → 等级与购买价格 → 属性/队伍人数/技能槽/洗点消费点。
7. 地牢：POI/挑战等级/楼层计划 → 实际房间生成与怪物选择 → 事件/奖励/通关/城堡门槛。
8. 自动挂机：合法目标选择、旅行速度、失败返村、城堡手动发起、循环收益；正式与模拟玩家行为隔离。

**图谱要求**：有多层消费关系时能沿「配置 → Loader → 规则/聚合 → Runtime → 结果/可观测证据」追踪；不重写任何正式公式。

## 4. M2-C｜六项高优先级深挖

### C1 属性与战斗公式

生成 `attribute_effect_matrix.csv` 的属性部分：**36 Key** 各自的默认来源、可配置性、Modifier聚合、运行消费点、UI/技能引用、是否被当前内容实际使用。对 M1 的约17项空投放逐一分类。

新增属性 Key 的最小变更面只做书面说明：注册、加载校验、聚合、伤害或行为消费者及模拟观测能力；不实现新 Key。

### C2 技能、天赋、Effect、Buff与召唤

覆盖现有**10类 Effect kind**（每种至少静态跟踪一条完整链；有可执行现有检查时再给运行证据），以及 **21技能、25 Effect、13 Buff、2召唤**的关联方式。

核对61个天赋的正式 `skill_id` 绑定与旧 `CastTalent` 路径，输出 **24个旧路径节点逐项清单及行为/效果表达差异**（以实际核对数为准）；不能简单假设旧新路径等价。

空 `trigger/proc_icd/proc_limit` 表需明确：加载与消费链存在，但当前配置零投放；不据此断言所有触发逻辑未实现。

### C3 星图（P2-3重点）

核对17节点及所有效果类型：成本、前置、最高等级、购买校验、消费方、应用时机、存档与洗点。形成**星图效果类型→实际消费点→新增同类节点能否纯配置扩容**矩阵。

特别区分：增加现有属性节点、增加现有功能解锁等级、增加**全新的功能规则**。第三类若需要消费者，标 `REQUIRES_EXISTING_SYSTEM_EXTENSION`，不擅自实现。

### C4 地牢房间事件

描述当前宝箱/营火的抽选概率、触发时机、收益/回复实现、角色状态变化及运行证据；给出 P2-3 若要事件表驱动时所需的**最小字段与最小 Core 扩展点**（只提案，不新增事件系统）。

### C5 怪物、精英与Boss

分别审计「49身份」「行为策略/行为包」「10词缀」「34Boss技能包」「章节加权池」「实际刷怪」；**不要把身份数、表行数、行为种类数混同**。列出纯数据新增身份/组合的边界及新增AI行为、阶段脚本的程序扩展面。

### C6 地图/关卡生成

澄清章节/共享配置覆盖次序、`floor_plan` 规划与 `Reveal` 实际刷新关系、难度及地图切换参数生效时机。指出任何配置看似已改但不能实际影响生成的字段。

## 5. M2-D｜有限运行验证与技术边界

本轮以源码审计为主，仅复用**已有测试**与最小测试侧观测来印证关键链路：

- `dotnet build`、全量 Core Checks、定向现有检查、必要的短场 Simulation；涉及 UI 适配时才运行 Godot smoke。
- 运行验证只声明实际覆盖的链路，不把一次模拟的综合结果冒充每个技能字段正确生效。
- P2-1-M3 的逐技能、攻击者、召唤事实仍处于 **`M3_COMBAT_FACTS_PENDING`**：必须标记 `UNAVAILABLE`，不可用零值补齐。若确需新增 Core 只读采集，先输出审批方案，不在本轮改 Core。
- 所有体验强弱、天赋/星图内容补充量、事件种类、经济目标，均留到 P2-3 正式设计。

## 6. M2-E｜P2-3内容扩容接口清单

从七项 `content_expansion_gaps.csv` 出发，输出 `expansion_interface_matrix.csv`，列明：

`system`、`existing_capability`、`candidate_content_extension`、`data_only_or_core_extension_or_out_of_scope`、`configuration_schema_support`、`new_consumer_needed`、`minimum_code_touchpoints`、`testability`、`missing_fact`、`P2_3_decision`。

优先级为：

1. 天赋/技能/属性的正式 BD 内容与表达能力。
2. 星图跨模块长期增量功能节点及消费方（重点专项）。
3. 地牢事件的配置与执行表达。
4. 怪物/精英/Boss的正式行为和遭遇内容。
5. 地图/挑战与实际刷怪的匹配关系。

装备、商店及其他独立新系统继续标 `OUT_OF_SCOPE_NEW_SYSTEM`；不能以「内容补足」名义要求本轮开发。

## 7. 交付物

**机器表（建议留在 `docs/data/`，与 M1 CSV 并列）：**

1. `parameter_registry.csv`：正式参数与非数值字段完整台账。
2. `formula_dependency.csv`：公式、输入、输出、依赖及消费证据。
3. `attribute_effect_matrix.csv`：36属性Key、Effect种类与运行状态/表达限制。
4. `runtime_consumption_matrix.csv`：配置→加载→消费→结果，重点链路独立可检索。
5. `expansion_interface_matrix.csv`：P2-3 各系统扩容接口与成本类型。

**人类可读报告：**`YYYY-MM-DD_HH-mm_data_p2_2_m2_parameter_runtime_audit.md`（按 `AGENTS.md` 现行约定；如有更近规范以仓库为准）。

报告应包括：配置和源码双指纹、142份 ACTIVE 表的覆盖说明、需要人工复核的动态/反射路径、实际验证证据、遗漏/悬挂/冲突、重点五系统结论、P2-3设计前置清单、M2放行/阻断裁决。

不要把成千上万条内容逐行复制进报告，明细放CSV，报告只写统计、例证、问题与决策。

## 8. 验收标准

- [ ] 142份ACTIVE CSV的字段覆盖能与 `config_manifest.csv` 完整对账；每列都有明确语义、归类或 `UNVERIFIED` 原因，跨章Schema合并不漏文件。
- [ ] 影响玩法的参数均能指向真实加载点与消费者，或明确标记 `LOADED_ONLY` / `PLANNED_ONLY` / `NO_CONSUMER` 等；不凭文件名推断运行生效。
- [ ] 关键成长、战斗、技能、星图、关卡、经济公式有依赖和顺序证据。
- [ ] 36属性Key与10种Effect全部单独覆盖；24个旧 `CastTalent` 节点（核实实际数）逐项归档。
- [ ] 17星图节点与现有效果消费者逐项核对；新功能节点扩容成本被明确分类。
- [ ] 房间事件硬编码、怪物身份与行为分离、楼层规划≠实际刷新等历史缺口有代码级证据。
- [ ] M3现有观测缺口继续明确标为 `UNAVAILABLE`；没有将静态确认冒充逐技能实测。
- [ ] 全程不改正式Core/数值/配置/玩法、存档格式或玩家进度；测试侧改动受控且有回归。
- [ ] 生成机器表和单份MD Review；解释所有尚未查清的字段/依赖，并明确M3仍需复核的项目。

**放行**：完成「配置到运行的全量映射」后进入 P2-2-M3「数值设计接口与内容覆盖验收」，再启动 P2-3「先补正式内容与必要规则，后进行框架性数值设计」。

## 9. 执行纪律

先审计真实代码和既有 M1 工具 → 设计字段字典与导出方式 → 补必要的只读/测试侧工具 → 执行检查与人工链路复核 → 形成机器表与单份 Review。

发现事实冲突先写报告，不自行改数值或玩法。任何需要修改正式 Core、改变既有机制、扩展生产 Schema 的内容，先列最小方案和文件范围，**等待批准**。
