# 设计权威、证据等级及跨系统差异合同

## 来源优先级（必须逐项核实）
1. 最新用户明确[C]裁决（例如六槽与每槽单主属性、CHARM只用ATK、不投放HP变体；坚韧药剂百分比减伤；Lmin禁售；直接操作升级而非自动升级）。
2. 有效产品纲要及已确认设计；子系统S06/S07/S09/S11等只对**已采纳**条目产生约束，未批准的候选[P]/[H]不可一律升级为[C]。
3. 用户授权范围内由模块Review记载的有效实施改动，解释工程事实[E]，而非产生新玩法授权。
4. 历史方案/审计、失效原型、模板与建议，只供追溯。

如果“设计Owner提出—工程近似实现—用户尚未确认”，标`IMPLEMENTED_DIFFERENT`，不能按工程现状反向覆盖设计。若用户已覆盖旧设计，标`SUPERSEDED_BY_USER`并列出旧条款与新裁决。对用户这次UI、卡点等反馈，记`USER_OBSERVED`，在设计侧另标`USER_REVIEW_OPEN`，并不自动表示代码错误或新玩法已批准。

## 证据强度
- `E0_UNVERIFIED`：仅文字声称或缺文件。
- `E1_STATIC`：表、源、ID、消费者入口存在但未观察实际效果。
- `E2_RUNTIME`：固定种子实际操作/事件/对照、运行时读取效果、守恒或行为截图有出处。
- `E3_GODOT_UI`：真实Godot窗口状态前后、交互序列和可读性证据，可同E2并行；自动化点击不等于用户人工体验。
- `USER_OBSERVED`：用户实际体验或操作反馈，作为问题线索及可用性评审证据，须保留原话语义。不能被自动化PASS覆盖。

**结果分层**：工程E（已报告并核对的事实） / 设计V（设计Owner复核） / 用户V（体验或产品裁决）。工程自检PASS != 设计接受 != 用户体验合格。

## 主状态（唯一）
`MATCHED_EVIDENCED` 设计与行为一致且证据充分；`IMPLEMENTED_DIFFERENT` 有实现但关键语义变更/近似；`DESIGN_UNDECIDED` 源设计自身含相互冲突条款/未确认取舍；`NOT_IMPLEMENTED` 确认缺少实际消费者；`NOT_VERIFIED` 无法证明；`SUPERSEDED_BY_USER` 原设计已被用户覆盖（需同时核对生产是否落实）；`OUT_OF_SCOPE` 明确后置。本字段不得使用“自检PASS”混写；测试PASS另列。

## 决策建议（不等于执行授权）
`KEEP_MATCH`、`NEEDS_ENGINEERING_FIX_PROPOSAL`、`NEEDS_DESIGN_SPEC`、`NEEDS_USER_RULING`、`DEFER_EXPERIENCE`、`NEEDS_RUNTIME_EVIDENCE`、`SUPERSEDE_OLD_REFERENCE`。建议里写改动范围、代价、与其它系统影响，但不直接改源。

## 必须保存的冲突链
`DesignId/IssueId | old_rule/source | new_rule/source | evidence_current | delta | suggested_owner | dependency | user_ruling_needed | status`；不允许只给“旧表过期”一句话。
