# 02｜跨所有专项的统一验收合同

## 1. 两种测试真值不可混淆

- **Core逻辑事实**：动作申请、被拒绝原因、属性快照、伤害、死亡、奖励、状态生命周期等；权威在 `Game.Core`，Godot可视化不是逻辑真值。
- **Godot/Mini体验事实**：受击反馈、入口拥堵、火球/多重箭视觉可读性、粒子数、卡顿、退让自然程度；逻辑测试PASS不代表体验PASS。

## 2. 用例层级和定义

| 层 | 稳定前缀 | 重点 | 失败不能绕过 |
|---|---|---|---|
| 规则单测 | `QA-Rxx` | 护甲、4+1、Hit/Proc、Buff、尸体、经验 | 任何数值调平 |
| 战术AI回归 | `QA-Axx` | 接敌、入场、远程、目标、退让、技能动作 | 房间/职业对比 |
| 五职业功能 | `QA-Cxx` | 单人1槽、4人5槽、多光环诅咒召唤 | 配队排名 |
| 装备与存档 | `QA-Exx` | 开箱/词缀、来源、换装、跨进程Load | 掉落/经济结论 |
| 五章与Boss | `QA-Wxx` | POI、Castle、三古代人、混沌五封印、巴尔五波 | 三难度内容结论 |
| 连续挂机与性能 | `QA-Pxx` | 连房HP、收益每小时、事件峰值、Mini | 发布候选 |

`data/test_catalog.csv`中每条用例都必须有前置能力列表和权威来源；上游未实现则 `BLOCKED`。导入已有 P0-2 AI01–AI20、P1-4 AI01–AI30、P1-5 EQ-01–EQ-30、07章节矩阵和 G01–G06的测试时，务必**保留原始来源ID，使用 `source_package` 区分重名 AI01**，不要篡改原文的PASS语义。

## 3. 跨专项最容易漏掉的不变量

1. **攻击者等级**驱动物理护甲 K(L)，角色/怪物/召唤无第二套减伤；独立来源下五伤害正确区分护甲/抗性；五伤害类型不默认赋予元素异常。
2. 4 常规乘区（技能、通用、威能、易伤）+独立暴击因子；相同来源不能因为装备或双光环重复注册。
3. 伤害、致死、死亡事实、尸体产生、EXP/金币/宝箱各按自身资格唯一结算；敌召唤反复死亡不能无限刷收益。
4. 近战容量满后的后排漏怪清晰且确定性；容量0仍可被多只攻击；远程普通怪不占容量；Forced/临时Overflow生命周期有效。
5. 入房敌AI延迟、小队入房散开不回退；角色退让不改怪物目标、不越界、不抢断Cast。
6. 同一英雄仅一活动动作；CD仅Commit触发；技能无目标则不空放，普攻兜底；初始1人1槽，四人上阵与5槽合法进度可配置测试。
7. 圣骑士多光环各占槽同时维持；同类增益不无限叠加；死灵多诅咒共存。
8. 主人临时光环不默认重复继承到召唤物；骷髅不需尸体、跨房保留HP/数；复活尸体唯一消费、数量/持续时间上限。
9. 游侠**只弓**；多重箭/旋风/连锁闪电是真命中，但Proc有界；同一伤害不可同时走两份结算。
10. S3手动开箱才固化物品实例、满仓丢箱；S4换装安全边界、源撤销，真实新进程Load不重复挂Modifier。
11. 原五章源数据不被 Overlay覆盖；原有42区域/231POI/42Castle/三难度楼层预算身份保持；Boss的特殊关卡演员数量不叠加到普通怪池。
12. 同 Seed、Tick、版本快照 Core事实事件序列可复现；渲染帧率仅影响表现。日志/Trace有界。

## 4. 本包对上游专项的依赖不是“已经实现”

`data/prerequisites.csv` 对每个能力记录 `UNKNOWN` 起始状态。Claude用源码、测试和提交证据更新为 `IMPLEMENTED` 后对应场景才可真正跑；未批准的正式公式、Boss候选、装备词缀值则保持 `APPROVAL_PENDING`。

## 5. 失败分类必须有因果证据

`LOGIC_BUG`(违反规则)、`MISSING_FEATURE`(尚未开发)、`SPEC_CONFLICT`(版本冲突)、`CONFIG_INVALID`、`BALANCE_OUTLIER`(逻辑正确、差异异常)、`VISUAL_ISSUE`、`PERFORMANCE_ISSUE`、`INSTRUMENTATION_MISSING`；分类不同，不能都通过改伤害系数解决。

## 6. 验收的断言示例（不代表已经实现）

- `QA-R01`: K的攻击者等级变大，在相同Armor、Raw下实际物理减伤不升高（要求已批准的K曲线单调）及有效承伤测试；`K`若未批，用`TEST_ONLY`夹具测试公式代数，不可通过生产迁移门禁。

## 7. 准出状态

# 03｜综合测试采集、去重与可复现对照规范

## 1. 标准实验标识

`RunID, CommitHash, ConfigRevision, ScenarioID, DifficultyID, PartyPresetID, Seed, StartTick, EndTick, CoreBuild, ApprovalRevision`。必须可区分同一存档在不同设置下的结果，不能以本机墙上时间决定逻辑事实。

**时间基准**：游戏逻辑Tick及其明确换算的模拟战斗秒。挂机每小时收益需同时给出「在线真实小时」与「有效模拟战斗小时」，处理暂停、进出菜单、失败复活、加载等时间口径，不把5分钟加速测试伪称真实一小时。

## 2. 核心事件字段建议

遵循 `data/telemetry_schema_TEST_ONLY.json` 语义，**这是采集约定，不要求新增同名C#类或复制整个事件流**。可复用现有日志、Debug UI、EventBus导出；快照需有来源ID，Trace过大时允许分层聚合和有界采样。

| 类别 | 最低事实 |
|---|---|
| DMG | Source/Owner/Target, DamageType, Raw/EffectiveHPRemoved, Crit/Dodge/Block, ArmorK, resistance, 4+1分区贡献, tick |
| Skill | Slot/SkillID, candidate/rejectReason, Cast Windup/Commit/Recovery/CD, TargetPolicy, result |
| AI | UnitID, normal/overflow/forced, target, retargetReason, engagedReservation, partyEntry/AIStart/Retreat |
| Buff | SourceID, StackGroup, target, effectiveValue, add/remove/tick |
| Summon | Owner, Type, HP, engagement, alive count, reason spawn/despawn, room transfer |
| Trigger | triggerSource, procEligible, ProcChainID, depth, count, limit/rejection |
| Kill/Loot | DeathFactID, RewardFactID, eligible, EXP hero allocations, Gold, chest/item provenance, corpse consumption |
| World | Act/Region/POI/Dungeon/Floor/Difficulty, EncounterID, BossPhase, CastleApproval |
| Performance | fixed Tick cost p50/p95/p99, eventQueuePeak, actorCount, effectCount, Mini render FPS, memory trend |

## 3. 指标口径（只算真实有效贡献）

- `EffectiveDPS` = 全队对合法敌人造成的**实际HP扣除量** / 合法攻击模拟时间；过量伤害单列。
- `TTK` = 从战斗合法激活到有效敌人清空；另记录入场延迟，避免因不同AI延迟比较时产生虚假的“伤害更高”。
- `RoomClear` = 完成事实、合法刷怪/召唤计数清零；不得以当前屏幕无怪但队列仍待刷视为通关。
- `Survival` = 角色死亡、各角色剩余HP、召唤损失、连续成功房间、失败重试与是否需要玩家干预。
- `ControlContribution` = 有效控制时间按目标去重，不把同一目标两层冻结时长简单相加。
- `Aura/CurseContribution` = 相同seed/配置/队伍，只开关一项合法效果，估计其他成员的增量贡献；**承认路径变化会引入比较噪音**，需多seed配对。
- `ProcRate` = 合格触发次数/合格输入事件数及单位模拟战斗时间两种口径；无资格的DoT Tick不进入直接Hit分母。
- `Loot/EXP_per_hour` = 合法奖励事实/在线时间，同时记录重复挑战、手动开箱延迟及满仓损失；不可只看随机掉落总价值。
- `VisualReadability` = Mini下是否能判断谁在被攻击、施法有效否、出怪/入场/光环视觉边界；采用录像人工验收。

## 4. 对照实验顺序与置信要求

1. 同一 Commit、配置、角色等级、技能点、装备实例/价值、困难等级、怪池、Seed、固定Tick和入场延迟条件；**只改变一项**。
2. 使用成对 Seed 列表：相同Seed先跑A，再跑B；顺序可反向复查，防止状态残留；每组配对记录差异而不仅均值。
3. 先通过单Seed复现和异常边界；再进行多Seed观测；后用Bootstrapped CI或分位数查看稳定性（参数阈值待审批）。
4. 重要指标至少报告`N`,均值/中位数,极值或p95,失败率、原始RunID。**不能因为平均TTK更低，就忽略大幅增加的挂机死亡率。**
5. 区分功能回归阈值（应精确断言）与平衡目标区间（待用户批准）；前者不应通过“±10%容差”掩盖重复奖励等Bug。

## 5. 统一结果样例

`data/telemetry_run_example_TEST_ONLY.jsonl` 只演示字段，不是来自用户实机。正式采集如规模大可导出结构化摘要并记录权威原始日志路径；无权威输入则 `INSTRUMENTATION_MISSING`，不能凭肉眼推断具体Proc次数。

# 04｜数值调平流程（不预设平衡结果）

## 1. 必须按依赖顺序进行

**阶段0：验证系统正确性 → 阶段1：单体攻防基准 → 阶段2：职业单独可玩 → 阶段3：怪群及四人协同 → 阶段4：三难度与掉落成长 → 阶段5：长挂机稳定性 → 阶段6：Mini表现签收。**

禁止在伤害结算和护甲迁移仍失败/待审批时通过改怪物血量、技能CD或装备增伤，伪装已实现的平衡。

## 2. 宏观数值的优先观察口径

| 问题 | 必须先排查 | 最后才调整 |
|---|---|---|
| 所有英雄都打不动Boss | K(L)、怪物护甲、4+1、技能是否正常命中、攻击动作 | BossHP/Armor/单体技能倍率 |
| 多重箭显著超过所有技能 | 每次释放重复命中、Proc资格、穿透、攻击速度与有效HP扣除 | 多重箭伤害/箭数量 |
| 远程被贴脸秒杀 | 接敌容量、后排合法站位、退让是否已实施、入房散开、AI延迟 | HP/护甲/远程自保技能 |
| 召唤流无敌 | 召唤战损是否保留、骷髅接敌是否被正常追击、外部光环双继承 | 骷髅HP/数量/召唤CD |
| 圣骑士+死灵使队伍数倍增伤 | 光环/诅咒来源重复、相同组是否累加、信念+降低抵抗是否只改抗性 | 具体光环/诅咒强度 |
| 尸爆一招清空Boss | 尸体资格、尸体强度上限、无限触发、Boss目标免疫/上限 | 尸爆伤害系数 |
| 挂机收益爆炸 | 召唤怪奖励资格、重复死亡、宝箱手动开箱、满仓丢箱、失败收益规则 | XP/Gold/掉率与成本 |
| 越级练小号异常 | 怪-英雄等级EXP倍率、所有已上阵全员EXP、死亡成员奖励 | 等级衰减倍率 |
| 法师冰系永久控制Boss | Boss状态抵抗、控制刷新、固定Tick和CD、AI错误空放 | 冻结持续时间与CD |

## 3. 调平的主控变量与次序

- **物理攻防**：确认生产 `K(攻击者等级)` → 统一五类型抗性 → MonsterAttack/Armor成长 → 技能基础系数。K曲线调整会影响所有物理BD，应单独版本批准。
- **职业**：先比较基准普攻与单技能，再比较单人/双人/四人队；职业贡献分输出、生存、协同，不能只按个人DPS排队。
- **怪物**：控制怪物行为类别、数量、激活延迟、刷怪波次，再改变HP/伤害/攻速；Boss阶段时间是否合理与Boss HP独立观察。
- **装备**：先验证装备实例与词缀生效，再比较相似价值装备A/B；不要让未确定品质掉率干扰战斗系数调平。
- **长期成长**：每难度前/中/后抽样，针对可实际到达的角色等级、技能点、装备价值；没有达成正式等级曲线则使用标签清楚的TEST_ONLY样本。

## 4. 不采用统一DPS目标

例如野蛮人坦克、圣骑士光环、死灵多召唤，对团队的贡献不能简化为同个人DPS。至少同时报告：`RoomClearTime、Deaths、SuccessRate、ResourceUptime、DamageTakenBySummons、Buff/CurseAblationDelta、EffectiveDPS、Performance`。

## 5. 参数调优审批工作单

| 字段 | 要求 |
|---|---|
| ExperimentID | 不重复稳定编号 |
| Cause | 先确定是逻辑Bug、配置非法、缺能力还是合理但失衡 |
| ChangedParameters | 仅允许经批准的1～2个明确参数，不“整包微调” |
| Baseline/Variant | 两组有相同种子、编译版本、队伍、地图、装备价值与时钟 |
| Effect | TTK、死率、收益、CPU及变差项均汇报 |
| Rollback | 可恢复旧配置版本与种子结果 |
| Decision | USER_APPROVED / REJECTED / NEEDS_MORE_DATA |

每项调整需要`ConfigDiff`且有可回退版本；不可让Claude直接写入现有正式五章掉落表/怪物池而不经审批。

## 6. 调平建议的方向性、不作为生产阈值

- Normal：保障单职业可开局、基本队伍可推进；让玩家理解技能与怪物类别。
- Nightmare：要求逐步形成技能/装备BD，应出现不同怪物组合的相对优势。
- Hell：允许更高构筑挑战和卡点，但不能因为未确认元素免疫、Boss零尸体就让某类职业在未告知机制下永久失效。

**不在本轮锁定各难度通关时长、BossTTK、基础HP、每小时EXP/Gold、出货率或性能达标数值；这需要真实跑批和用户审批。**

- Mini 480×240下3~4英雄＋召唤物、怪物特效可能遮蔽锁定与击杀；必须有录像。

- 一维逻辑X/二维视觉Y；不允许因为测试夹具大场景迫使实现真实物理避障。

## 状态判定

- `PASS`：该层对应的实际命令/场景运行并满足断言，证据可访问。
- `FAIL`：已执行但断言失败，带失败详情。
- `BLOCKED`：尚无上游功能、TBD待批、合法存档/样本不可用。
- `NOT_RUN`：没有运行；不能标PASS。
- `INCONCLUSIVE`：数据不足或仪表缺失，即使表面数值符合也不能定平衡。

# 09｜P0-1 护甲固定减法→递减百分比：独立执行补遗 V1.0

> 这份补遗填补原主Todo始终未核实交付的**独立护甲改造执行规范**。它不是“护甲已经改好”的报告。全部实际行为由用户本地Godot源码审计确认。

## A. 已批准业务合同

- 物理护甲使用递减百分比减伤：`DR=Armor/(Armor + K(L))`，其中 **L为攻击者等级**；物理伤害`D_postArmor = D_preArmor * (1 - DR)`。
- `K(L)` 应可配置为明确等级曲线，最终生产值与定义由用户审批。
- 角色、怪物与召唤统一物理护甲规则；元素伤害按各元素抗性，不被Armor二次削减；五伤害类型不新增魔法/真实绕过。
- 4常规增伤乘区`M_skill/M_general/M_power/M_vulnerable` + 独立暴击`M_critical`，不因护甲迁移改组/增删。
- DMG2事件（闪避/暴击/格挡/击中/击杀）与DMG3数值结算保留现有权威流程，不另建DamageCalculator。
- 玩家已明确不使用固定减法Armor作为正式物理减伤模型；当前源码仍可能有减法分支必须通过审计证实。

## B. Q0必须只读审计

搜索`Armor`, `Damage`, `Physical`, `Resistance`, `Hit`, `Block`, `Crit`等的**实际C#代码引用与配置**；定位 Hero、Monster、Summon、装备Buff影响护甲、快照版本、UI的战斗详情与旧单元测试。

列出每条计算路径；确定：是否先减法后百分比、是否存在怪物特殊旁路、如何处理负Armor、K为0、等级0或超出曲线、逐击取整和最小伤害。**这些边界未获批不得偷偷选择。** 若原先确已使用正确百分比模型，仅补差异测试，不重复修改。

## C. 正式与TEST_ONLY的分界

单元测试可以注入`K=100`、`Armor=100`、`RawPhysical=100`作为**代数验证夹具**，预期减伤50%、剩余50；这绝不意味着等级1或任意等级生产 `K(L)=100`。

对于`Armor=0`、`K>0`物理减伤应为0；`Armor>0,K>0`时`0<DR<1`，随Armor增大DR递增但收益递减（相同K下）。`Armor=100,K=100`时`DR=0.5`。对攻击者等级L增加导致K变大一事，**必须在审批正式曲线后才断言全区间单调**。

## D. 向Claude请求的具体方案

1. 提交最小替换位置：现行伤害管线已有的物理减伤步骤；任何公式复制分支必须提出清理方案。
2. 给两至三套可配置 `K(L)` 候选曲线及覆盖低/中/高等级怪物伤害的对照，不锁正式数值；同时提供越级/低级刷怪跨级曲线的变形风险。
3. 要求用户批准：`K(L)`曲线、异常等级/护甲处理、逐击取整、旧存档/旧配置迁移策略、UI面板说明。
4. 批准后只修改被审计证实的最小伤害环节与配置加载/校验；删除授权废弃的减法公式来源，不留下两个结果或额外伤害乘区。
5. Core测试覆盖：Hero→Monster、Monster→Hero、Summon→Monster、元素护甲隔离、Crit/Block、穿戴装备护甲、负抗、异常K、确定性复演、跨进程存档读取。
6. Godot/Mini录屏：同一护甲值、同一Raw物理输入，显示的HP扣减与Core一致；同样场景两攻击者等级的差异与已批准曲线一致。

## E. 原子完成定义

- 审计前：`DOC_DELIVERED`、`CODE_UNKNOWN`。
- 生产K及边界审批后：`APPROVED`。
- 新公式真实编译测试通过且回归(含五伤害、4+1、召唤、装备)、新进程读档、Mini实机一致，旧废弃计算清理证据齐备：方可 `IMPLEMENTED/CORE_PASS/GODOT_PASS`。
- 否则保留 `BLOCKED/NOT_RUN`，**不得在08总报告中将护甲迁移标为PASS**。

# 10｜原主Todo完成后的下一阶段：讨论提案（未批准）

## A. 此阶段完成的是“设计交付包”，不是完整游戏

五职业 / 八怪实验 / 自动技能AI / 五章内容 / 装备BD / 综合测试包均已有首批交付文档；但没有用户本地Game.Core与Godot实机结果，所有上线与验收必须继续跟踪，尤其P0-1护甲K曲线和迁移。

## B. 下一阶段建议从“单系统能力实现”切换为“完整冒险体验与长期经济”

之前设计已经明确核心产品：Windows Mini挂机战斗 ↔ Management管理、五章地牢冒险、回城补给与换队、手动开箱打宝、永久星图、角色等级/技能树/装备BD、不强制转生。下阶段无需重新发明核心循环，而是优先做**完整连续冒险中玩家做出选择的强度与频次**，让已开发系统形成可感知的游戏体验。

### 候选三条方向（建议按依赖顺序）

| 建议顺序 | 方向 | 设计/开发重点 | 最小验证结果 |
|---|---|---|---|
| 1 | **V2 冒险—打宝—成长闭环** | 自动推进和回城恢复、掉落/开箱、装备替换、升级加点、星图开放与卡点、下一目标；首章选一条可完整走通的路径 | 从新档单英雄到小队解锁、打Boss、变强再挑战的连续可玩段，管理界面与Mini衔接自然 |
| 2 | **Loot 与成长经济纵深** | 装备部位品质、词缀池、物品等级与区域、金币消耗与星图、宝箱容量/开箱节奏、经验/技能点曲线、三难度可达目标 | 从早、中、晚期三个档案测得升级与换装的明确决策价值、收益时长分布和经济消耗闭环 |
| 3 | **可观赏性与桌面产品体验** | Mini窗口信息层级、弹道/伤害反馈、入门散开、召唤遮挡、世界导航与挂机状态可视化、窗口切换性能、离线收益展示 | 480×240连续挂机体验可读、无严重拥堵与无效动作，桌面置顶/交互顺畅 |

## C. 我更推荐先落地哪一个？

**推荐：方向1《冒险—打宝—成长闭环》**。理由：即使战斗/装备/怪物都能单独运行，若玩家不知道下一次该升级哪项、为什么继续刷怪，实际留存体验也不会成立。该方向会直接串联已确定的世界地图、地下城、城镇、手动开箱、星图与队伍编成，能够暴露系统组合的缺口。方向2与3与其并行提供小规模支撑，不建议整套战斗重构。

## D. 下一轮讨论建议固定回答的问题

1. **首个可玩体验范围**：选择Act1从新建存档到安达利尔，还是更短的首章核心路径？（用现有合法POI/地图，不改拓扑）
2. **前60~120分钟的成长节奏**：何时出现新的可做决策（升级、开箱、换装、天赋与解锁上阵位），不要强制人工高频操作。
3. **卡点与自动挂机**：当前卡关后重试/刷收益/手动选择提升什么，如何通过UI解释“下一目标”。
4. **经济与角色成长**：金币/星图/装备/技能点的边际价值，哪项作为主驱动力；哪些需要完成正式数值审批。
5. **明确不做什么**：不引入强制Rebirth/Prestige、AP重置，不改变已有五章地图/城镇/房间战斗架构，不扩到5人首发。
