# 01｜技能 BD 交互与平衡规则 V1.0

> 状态：**G01–G06 核心原则 Confirmed（C）**；本规范中的排序/实例细节为 Recommended（R），数值、精确 API 为 TBD（T）。
>
> 设计目标：保留多光环、多诅咒、多段攻击、骷髅军团与尸爆连锁的爽感；统一判定来源，阻止重复乘算、重复发奖和无界事件派生。
>
> 非目标：新建第二套伤害、事件、Buff、召唤 AI、存档或奖励真值；立即锁定技能伤害、CD、数量、持续时间、链深数值。

## 0. 必须复用的既有核心合同（C）

- 战斗 Core 固定 Tick；`Game.Godot` 是表现适配器；所有玩法数值以 Core 为权威。
- **单一 DMG 管线**：DMG1 解析快照 → DMG2 前置命中/闪避/格挡/暴击事实 → DMG3 分类型防御与 **四常规增伤池 + 独立暴击因子（4+1）** → 原子 HP 应用 → DMG2 后置命中/受伤/击杀/死亡事实。混合伤害按分量分别防御。
- 既有四池：`M_skill`（技能基础系数及系数增量），`M_general`（通用百分比），`M_power`（数值型装备威能），`M_vulnerable`（易伤）；池内加算、池间相乘。**不得新设光环池、诅咒池、召唤池或 Proc 池**。
- `Skill` 管 Windup/Commit/Recovery 与 CD（Commit 开始）；`Effect` 管离散效果；`Buff` 管状态/属性贡献/周期；`SkillModifier` 在合法扩展点生成有效技能规格；`TriggerRule` → 确定性 `EffectQueue`。
- 玩家/怪物共用战斗事实与伤害入口，二者各有 AI Policy；AI 只提出 ActionRequest，不在事件监听器中直接取消技能或改变 HP。

## G01｜Buff 与 Debuff 聚合（C）

### 1.1 规则

1. 同一属性的可叠加普通数值修正沿用现有 `AttributeModifier` 的聚合合同 `(base + flat) × (1 + pct)`；概率类/抗性类按各自已有合法规则处理。**不要**笼统把所有属性都套这一个公式。
2. 所有增伤按**语义**映射到既有4+1体系。例如“光环给予物理伤害+%”进入 `M_general` 的适用贡献；“目标受到物理伤害+%”若属于易伤则进入 `M_vulnerable`；“降低火抗”进入**防御抗性解析**，不成为第二个 `M_vulnerable` 或新乘区。
3. 异常状态（冻结、减速、眩晕）、属性修正与规则型触发可以共存，但其合法性分别由 Buff/Effect/Trigger 合同约束；`Buff` 只有一个有效实例来源，不因周期刷新重复注册 Modifier。
4. 多种不同主动光环**可同时维持**（每种占1技能槽）；多种不同主要诅咒**可作用同一目标**。不得强加“一个光环/一个诅咒”的暗中限制。
5. 同一效果重复施加默认不无上限叠加；应提供受控语义（较强者生效、刷新持续时间、有限层数、独立来源等）。**具体每个 Buff 的策略不是统一硬编码默认值；需要现有 schema/设计审查及测试。**
6. 辅助来源不应把技能增益、护甲减伤、易伤、减抗全部放进一个巨大通用数值池；需要严格归属、避免重复消费同一贡献。

### 1.2 示例（R，非生产数值）

| 场景 | 合法结果 | 非法结果 |
|---|---|---|
| 同一圣骑士维持狂热+信念 | 两个技能各占槽，攻速/元素减抗分别生效 | 系统只容许“第一个光环”，或隐藏新增光环乘区 |
| 两名圣骑士施加同一光环 | 按该 Buff 专项“同名取强/刷新/有限层数”策略处理 | 每个固定 Tick 无上限叠加数值 |
| 死灵同时施加伤害加深+衰老+降低抵抗 | 三个不同诅咒均可存在，分别影响物理易伤/行动/抗性 | 新诅咒自动无条件覆盖所有旧诅咒 |
| 信念+降低抵抗 | 对目标元素抗性产生统一修正，经过批准的上下限截断 | 减抗之外又额外各乘一次全局增伤 |
| 召唤物位于狂热光环范围 | 当目标过滤允许，召唤物独立接收 Buff | 主人身上的光环通过继承再乘一次，召唤物本身又乘一次 |

### 1.3 审计要点（T）

- 现有聚合器如何表达4+1的易伤、技能系数与威能？条件加成属于 DamageModifier 还是 AttributeModifier？
- Buff 实例唯一 ID、来源 ID、StackGroup 及刷新顺序是否已有？是否需要对旧配置迁移？
- 光环范围、存活/离场、队友和召唤物资格，是否已有有效对象过滤机制？
- 当用户已装备多个光环，但技能槽变动、施放时序与死亡复活发生时，哪些光环保留？未定不得固化。

## G02｜同源重复与状态生命周期（C）

1. 同一个 Buff 实例合法移除至多一次；对应 Modifier 与 TriggerRule 订阅必须彻底注销，Dirty 快照随之正确更新。
2. 诅咒不是全部共用一个槽位；相同 ID / 同 StackGroup 的重复行为按已批准的单项策略处理，不同诅咒彼此独立。
3. 光环是“持续维持”的主动效果，装备每种占槽；不应为了维持效果每 Tick 都重新走一遍 Windup/Commit 造成无意义动作。**光环首次激活/续存的准确生命周期和场景过渡行为：T。**
4. 不同主动光环可以共存，光环与被动常驻 Buff 应按来源明确区分。多角色同名光环默认推荐择强而非线性叠层（R，需核对既有 Buff 策略）。
5. 对效果撤销、倒计时、范围出入，要求**来源可追踪、确定性、不会永久残留**。

## G03｜多段 Hit 与 Proc 触发资格（C）

### 3.1 术语与判定（概念，不强制新类型）

| 概念 | 含义 |
|---|---|
| `Cast/AttackAction` | 一次施法/普攻动作，可能生成多个伤害实例 |
| `DamageInstance` | 对一个目标的一次逻辑伤害结算，可包含多伤害分量 |
| `HitConfirmed` | DMG2 判定命中事实，不等于最终正数伤害 |
| `DamageDealt` | 扣血的正数伤害事实，不等于死亡事实 |
| `ProcEligible` | **特定** TriggerRule 对特定来源的资格，不代表所有命中都能触发任意效果 |
| `KillConfirmed` | 原子 HP 应用后唯一一次合法击杀 |
| `OriginChain/OriginCast` | 便于事件队列追踪根源、避免同事件无限派生的概念关联 |

### 3.2 规则

1. 多段攻击每次合法命中都可正常调用 DMG 管线并结算伤害；**不得为了削弱 Proc，将真实伤害命中直接合并为一次**。
2. 一次真实命中**不自动**拥有所有装备/被动触发资格。TriggerRule 根据事件、来源标签、资格、触发次数/独立CD/目标去重检查。
3. DoT、地面持续效果不默认等同“直接武器命中”；其暴击/格挡/击中触发资格若旧合同未审批，须列 T，不可擅自设为全有效或全无效。
4. 同次多重箭多弹道命中同一目标、连续旋风斩、炮轰、持续暴风雪的重复命中，应分别在技能/触发规则中声明允许情况；**没有统一隐藏“所有技能一目标最多1次”的硬限制**。
5. **由 Proc 产生的派生伤害默认不自动获得无限再次 Proc 资格**；具有显式连锁授权的能力可以继续，但要有有界追踪机制（详 G06）。
6. 暴击是 DMG2 判定并作用 DMG3 的**现有独立事件因子**；格挡仍属防御；二者不是通过限制 Proc 伪造的额外乘区。

### 3.3 几个必须共同验收的例子

- 游侠多重箭射出5箭命中5敌：应发生5个合法 DamageInstance；某装备“每次施法最多触发1次”应按技能关联约束，而不是只允许第一支箭造成伤害。
- 野蛮人旋风斩持续命中同一敌：各段真实伤害可见；有 ICD 的装备触发频率受其独立 ICD 约束。
- 冰法暴风雪的每次 DOT/Tick：按自己的伤害事件发生，但不得假定每 Tick 都可按普攻命中触发吸血。
- 由“击中释放闪电”产生的闪电：不可无意自我递归；显式连锁例外须保留来源链 ID 与上限。

### 3.4 仍待批准的具体参数

`ProcChance`、`InternalCooldown`、`MaxTriggersPerCast/Target`、暴击/格挡/DoT来源资格、不同 Buff 几率加算/相乘方式、队列预算/稳定并列顺序等全部 **T**；字段名为 R。不能把示例数字当生产默认。

## G04｜召唤单位成长、独立接敌与来源（C）

### 4.1 基础能力

- 骷髅战士、石魔、女武神、骷髅法师等可攻击召唤单位应使用统一战斗 Entity/AI/DMG 规则；分别具有基础 HP、Attack、Armor、抗性、攻速、射程、属性与**非负整数接敌容量**。
- 近战怪是否把召唤物作为优先目标由已确认接敌模型决定；前排容量不代表物理阻挡；召唤数量不重新启用刚体。
- 骷髅基础召唤不要求尸体；骷髅与石魔及女武神是不同类型；复活术依赖尸体，且有**同时存在数＋持续时间**上限。
- 召唤物存活时跨房间保留 HP/数量并跟随；跨场景表现位置可以重建，战斗状态不可无故清零。
- 召唤物击杀不改变上阵所有英雄按等级差获取 XP 的现有规则。召唤物自己死亡、重召唤不得产生正常怪物奖励或无限尸体。

### 4.2 来源与继承

推荐有效属性拆分：**召唤单位基础值 + 技能/天赋成长 + 经过批准的主人可继承属性 + 召唤物自己收到的动态 Buff/光环**。

关键保护：**主人身上来自外部临时光环等 Buff 不默认再次进入继承快照**，若召唤物也直接接受该光环，可避免重复收益。主人身上的特殊召唤词缀是否纳入继承，需精确设计配置语义。

| 待定项 | 不能私设的原因 |
|---|---|
| 快照时点与技能改装/跨房间刷新时机 | 影响装备切换后召唤属性是否瞬间变化 |
| 属性继承列表、百分比、取整 | 影响独立召唤 BD 和装备效果 |
| 召唤技能卸槽、主人换队/死亡后的召唤存续 | 涉及已确认的回城换人及存档、技能槽语义 |
| 角色/召唤物上限以及表现预算 | 影响战斗数值和 Mini 视觉可读性，不能靠假设数字定稿 |
| 主人死亡后其召唤是否继续战斗 | 必须与当前房间胜负及团队状态规则一致 |

### 4.3 来源与归属建议（R）

事件内保留召唤物实例ID、主人ID、产生技能ID和奖励资格标记；召唤物伤害按其自身攻击单位结算，击杀事件关联主人；玩家 EXP 和收益根据队伍及奖励资格合同统一核算，禁止召唤物单独私发奖励。

## G05｜唯一死亡、奖励结算与尸体唯一消费（C）

1. 有效 HP 降至死亡阈值后，单位只允许有**一次正式死亡状态变迁、一次有效死亡事实**；同 Tick 多段伤害不应重复发出 `KillConfirmed`。
2. 经验/金币/掉落等已确认收益**只能按合法一次击杀结算一次**；战斗失败重试不回滚已合法收益，也不重复结算同一个死亡实例。
3. 合法怪物可产生**至多一条可消费尸体权利记录**；是否生成由来源与技能/怪物资格决定。**不是所有单位都必须产生尸体**。
4. 尸爆与复活术对同一尸体是**竞争消费**；成功消费后其他尝试失败，不允许双方都拿到尸体使用权。
5. 击杀被动、金币/经验、其他合法 Kill Trigger **不等于尸体消费**；可以与“创建尸体”同时成立。不要把所有 Kill Trigger 都设计成只能有一个订阅者。
6. 一具已消费尸体不可再被复活或尸爆；召唤物、复活怪、特殊 Boss、重复产怪等尸体与奖励资格应单独配置。普通反复召唤出的敌人不能成为无限经验/物品漏洞。
7. 同一房间清理/切换场景需要释放尸体引用与对应 Trigger 中的无效引用；跨房间尸体默认不作为可复用战斗资源，若现有房间持久化合同冲突须审批。

**可选实现建议（R）：**在现有死亡事实/Encounter 资源中挂合法的尸体消费 token，成功消费使用一次性状态转换；不能未经审核就创建独立持续运行的 `CorpseManager`，更不能把 Godot 尸体动画当权威资源。

## G06｜连锁派生与确定性事件队列（C）

- `Effect/Trigger` 派生的后续伤害须通过已有受控 `EffectQueue`，带来源关联、深度或等价约束；不得从事件监听器同步无限递归调用自己。
- **默认不自动无限派生**。火球击杀的爆裂、尸爆连锁、碎冰、装备触发必须**明确被技能/独立强化节点授予连锁资格**；相应最大深度、分支数或同源预算由技能配置及技术安全预算共同约束。
- 同一尸体一次消费、同一单位一次死亡与单链来源去重共同阻止重复结算。
- 连锁爽感需要保留：**技术安全预算不等于把所有技能都锁定为固定3次触发**。数值、每Tick/每链上限及预算耗尽后的具体分帧/丢弃策略仍 T。
- 事件顺序必须固定 Tick 可重现；对相同随机种子与相同输入，不因帧率、UI 逻辑或 HashMap 枚举顺序产生不同结果。
- 若执行预算到顶，不得静默丢失已确定有效的收益、HP更新或必需的死亡清理；如何推迟/拒绝**未提交**的派生效果需明确批准的队列策略。

## 7. 审计与验收原则

- 确认跨模块只存在一个：伤害公式真值、Buff 生命周期真值、触发事件队列真值、召唤实体状态真值、击杀奖励真值。
- 全面测试不同诅咒与不同光环共存、同名不同来源择强、来源失效完全回滚、可受攻击召唤物接敌容量释放、尸体唯一消费。
- 所有规则级测试均应是 Core 无头可复现测试；视觉演示额外在 Godot 中测试 Mini 模式的清晰度、特效数量与入口状态。
- 若当前实现与 Confirmed 合同冲突，**先报告用户，再确认修改范围**；不以“统一架构”为由强制删除、重建或隐藏旧代码。
