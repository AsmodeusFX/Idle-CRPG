# 05｜Debug观测、无头自动化与Godot实机验收

## 1. 为什么必须观测

本项目已经在实机发现入门堵门问题，并调整敌AI启动延迟和小队入场散开。因此未来怪物设计**必须可解释**：为什么怪物锁定法师，是容量溢出、特殊猎手策略还是因嘲讽结束？为什么远程不后撤？为什么召唤者持续生成？仅观察输赢不够。

## 2. 调试面板（复用已有能力）

在Godot开发模式中可以通过现有Debug UI或日志查看以下事实，**不要求新增同名组件**：

| 事实 | 重点字段 | 用途 |
|---|---|---|
| 进房阶段 | 房间ID、散开开始/结束、AI启动延迟和当前激活状态 | 验证不堵门，确认延迟未被覆盖 |
| 目标锁定 | 怪物ID、目标ID、普通/溢出/强制/远程/特殊来源 | 分辨漏怪和后排猎手 |
| 目标重选 | 上次原因、何时安排、何时安全边界执行 | 排查每Tick乱换目标 |
| 接敌占用 | 角色/召唤物ID、容量、当前Normal预约数 | 发现容量0误认为免疫或预约泄漏 |
| 近远程行为 | AttackMode、实际射程、当前动作、技能CD、动作阶段 | 看怪物不打/射手风筝问题 |
| 召唤链 | 召唤者ID、子单位ID、存活上限、当前数量 | 防无限生怪和重复掉落 |
| Buff | 来源、目标、叠加组、持续时间与失效原因 | 检验M08没有属性泄漏 |
| 房间完成 | Alive有效怪数、待刷/待召唤计数、完成判定原因 | 检验M07是否无限拖关 |
| 收益 | 敌方生成类型、可否奖励、死亡唯一Key、奖励发放次数 | 防召唤物刷收益 |

**Debug必须可关闭且容量有界**。默认不向正式档案写入全量怪物AI日志；Godot绘制临时目标线不能成为权威目标真值。

## 3. Core自动化测试（编号与不变量）

| Case | 条件 | 必须断言 |
|---|---|---|
| AI01 | M01面向容量3前排，其他队员尚不可被合法索敌 | 正常名额不超限，剩余不无故等待 |
| AI02 | M01面对0容量单人法师 | 仍能选择并攻击合法目标 |
| AI03 | 先前只有前排，后排在延迟/散开后成为候选 | 正常锁定稳定，Overflow仅安全重评 |
| AI04 | 容量2→3，对照固定seed | 有效Normal名额潜在增加，不出现预约双占 |
| AI05 | 2名前排和2后排 | 不用压力公式强制均分，锁定结果确定性 |
| AI06 | M02相对M01提高速度 | 同一目标规则，不自动获得后排优先 |
| AI07 | M04普通射击 | 远程占容量为0，近距离站定，不持续风筝 |
| AI08 | M05特殊AOE | 技能临时目标不永久覆盖普通锁定，不双结算 |
| AI09 | M06显式后排优先 | 仅合法后排目标可选，非瞬移/穿墙 |
| AI10 | M06被有限嘲讽 | Forced按既有规则生效、到期释放 |
| AI11 | M07重复召唤达到测试上限 | 同时活着子单位数不超过上限 |
| AI12 | M07仆从死亡并再次召唤 | 召唤来源可追溯，收益不能因回收ID重复发放 |
| AI13 | 召唤者死亡/所有有效单位消失 | Encounter按既有规则完成，没有无限待刷 |
| AI14 | M08施加Buff+源死亡/离场 | 实际Buff合同下到期/移除，快照不泄漏 |
| AI15 | 同Buff重复来源 | 按G01–G02叠加，不无限逐Tick堆积 |
| AI16 | 当前目标死亡/角色换人/房间退出 | 目标引用与容量预约归零，实体ID不复用泄漏 |
| AI17 | 同Seed同配置重跑 | Core事件事实序列相同（排除时间戳/非逻辑表现） |
| AI18 | Boss普通近战与特殊技能 | 普通目标与技能目标来源分离；不存在时BLOCKED |
| AI19 | 两种攻击模式合法切换（若既有支持） | 近/远程容量语义不串线；缺能力可报告BLOCKED |
| AI20 | 异常数据（坏原型ID、无效生成数量） | 强类型校验拒绝错误配置，不静默回退到生产默认 |

## 4. 入场、Retreat、碰撞回归（绝不能略过）

| Case | 回归条件 | 必须观测 |
|---|---|---|
| R01 | 角色入场先展开 | 保持现有PartyEntry逻辑，无复现严重堵门 |
| R02 | 敌人现有激活延迟 | 不因原型变更提前全部群起冲门 |
| R03 | 远程法师被近战真实命中 | 退让若已实施则依CD/合法目标移动，否则BLOCKED/NOT RUN |
| R04 | 退让触发时怪物锁定 | 退让不强制更换怪物主目标 |
| R05 | 房间逻辑X+视觉Y | 视效散开不改变Core合法攻击和距离 |
| R06 | 远程穿过/射向墙体与怪物 | 原有投射物持续碰撞和墙体限制保留 |
| R07 | 受击退让贴边/入口 | 不能越界与回到禁用入口保护区 |
| R08 | 召唤或BOSS特殊技能触发时 | Skill生命周期 Windup→Commit→Recovery，不在不可取消阶段同步重评导致双提交 |
| R09 | 死亡、重试、切房、换队 | 预约、Buff、召唤引用与房间临时状态清理正确 |
| R10 | DMG与EXP | 不产生第二套护甲/经验/掉落结算系统 |

## 5. Godot实机视觉验收

- T01：站位可看清前排承接3只左右（测试配置），溢出自然绕向后排；不要求视觉上完全无重叠。
- T02：12只快怪集中出现仍不长期堵住入口；退让表现自然且不频繁抖动。
- T03：重型怪攻击前摇明显，坦克承伤与团队治疗（若技能存在）可观测。
- T04：射手在射程内站定，投射物与怪物受击对应；T04-C有法术范围提示。
- T05：后排猎手确实构成威胁，嘲讽/救场有效且没有全图瞬移。
- T06：召唤生成、数量上限、死亡清理清晰；房间正常完结。
- T07：受Buff怪物具备容易识别的强化提示，来源消失后不残留错误效果。
- T08：Boss普通攻击与特殊技能目标区别清楚；若真实Boss缺失，则暂BLOCKED。
- Mini 480×240（当前规格约定）上仍能分辨怪物类型、伤害和技能特效；不能单在管理大窗口测试可读性。

## 6. Core模拟与视觉验收是两份不同的证据

- **Core PASS**：只说明对应逻辑测试通过，不意味着房间画面、入场散开或模型动画自然。
- **Godot PASS**：应有实际运行证据（录屏/截图、场景ID、配置ID、构建版本）；不是读取文档就算通过。
- **未执行：** 记录`NOT RUN`；依赖系统缺失：`BLOCKED`；断言失败：`FAIL`。**不允许统一写PASS掩盖分项失败。**
- 性能采集关注固定Tick耗时、事件队列量、目标评估次数、召唤活跃数与Mini帧率；基准阈值待真实工程测算，绝不编造达标值。
