2. 阅读**真实本地** `CLAUDE.md`、`docs/00_meta/DOCUMENT_INDEX.md`；随后查项目现有与如下主题相关的真实已签署文件和代码，不能仅凭本包中的旧规范摘录：
   - `docs/combat/BATTLE_AI.md`
   - `docs/combat/BATTLE_RUNTIME.md`
   - `docs/combat/SKILL_EFFECT_BUFF.md`
   - `docs/combat/FIGHT_ATTRIBUTES.md` 与 `ATTRIBUTE_MODIFIERS.md`
   - `docs/engineering/PROJECT_ARCHITECTURE.md`
   - 战场、AI、房间门口与角色入场、召唤物、Boss、目标锁定、技能、移动、投射物与存档相关的真实实现。
3. 搜索项目**已存在**的目标选择/目标锁定/目标评分/最近目标、仇恨、怪物已锁定列表、招架/盾卫/嘲讽、召唤物索敌、目标实例生命周期、重评请求、Combat配置、配置加载校验、单位碰撞/视觉错开。记录具体路径/方法/类型及当前行为。
4. 构建最小架构对照图：`Encounter spawn → combat unit activate/enter → TargetPolicy → lock runtime → Movement → Action/SkillRuntime → damage → death/target cleanup`；逐点标注**已经有/部分有/没有/不确定**。
5. 对照 `01_Combat_Targeting_Design_V1.0.md` 的 C01–C15，区分：
   - **A：完全兼容**：沿用现有组件只补少量功能；
   - **B：结构兼容，但需扩展**：写出字段、接口与配置迁移影响；
   - **C：规则冲突**：现有已确认设计与这版规则不一致，或实际实现的合同与新方案不同；
   - **D：无法判断/缺权威/涉及存档升级**：需要用户确认。
6. 输出 `Combat_Targeting_Preflight_Report.md`（草稿/报告文件可输出到任务工作区或聊天，但**不要改项目业务文件**），包含下面模板；不允许以“技术上能实现”为由自动处理 C/D。

### G0 审计的强制行为

- **发现冲突：必须停止有关实现，直接向负责人提问，不得擅自选新规则压过已确认旧规则，也不得静默保留两套规则。**
- **没有冲突，但要改变系统关键接口/权威字段：也必须先报给负责人确认。**
- 若某个条目是旧文档 `TBD`，可根据当前明确的新决策提出映射，但**不等于**可自行扩写不属于该决策的所有行为。
- 若实际本地文件缺失，请列为缺失并问负责人是否能提供/是否继续；不可把本包里的样例或旧历史文件冒充当前代码。

## G1｜负责人同意具体兼容方案后才能写代码

**不要把“方案全文由用户要求输出”误当成“授予在其本地工程自行覆盖已确认设计或做破坏性重构的权力”。**

审批内容至少明确：要修改哪些现有模块和文档、追加哪些配置字段/存档字段、如何处理单角色到小队差异、是否替换老 TargetPolicy、是否包含本期嘲讽/召唤物全部实现、测试标准。可以按无冲突子模块分阶段批准。

## G2｜最小增量开发（按顺序；每段验证）

1. 用现有目标锁定/MonsterPolicy接口新增**近战容量**资格判定及确定性预占，不更改远程默认最近目标与 PlayerPolicy。
2. 新增 `Overflow` 元数据/等价状态；补入场/召唤/目标死亡的重评请求和安全决策阶段的容量释放。
3. 完成后排容量0、全队无坦、双前排、动态容量变化等核心测试。
4. 在现有 Skill/Effect 接口上处理 `Forced` 嘲讽、救场目标切换；技能缺失则只留扩展口并标记 BLOCKED，不虚构正式新技能数值。
5. 在现有表现组件中追加虚拟站位/视觉Y偏移；**不增加战斗单位物理碰撞**，不影响逻辑 X 与投射物扫掠。
6. 调通混合近远程、召唤、Boss/特殊技能；如相关技能功能未就绪，只完成对应合约的可运行测试夹具，不谎称实机功能已经可用。
7. 必要且获准时进行存档/配置升级；显式检验旧数据，不自动覆盖已有CSV与Godot资源。
8. 最后做回归、跨模块差异审查、逐项清理被确认废弃的代码。未经审计与批准**不能直接删除旧代码**。

## 零垃圾代码约束（贯穿G0–G3）

- 只允许**单个权威 TargetPolicy/LockRuntime 路径**：不得让“旧仇恨模型 + 新容量分配器”并行生效，也不得在 Godot Node 和 Core 中重复决定怪物目标。
- 不新增 `TempTargetingV2`、`LegacyTargetingFallback`、万能 `CombatManager2` 或独立事件总线来绕开核心接口；一旦发现既有类似组件，优先复用或上报迁移。
- 不使用 `try/catch` 静默吞掉配置错误，不用神秘默认值掩盖缺失ID，不使用永远开启的临时 Debug、假掉落/经验等便捷实现。
- 不无端改变已有伤害公式、投射物连续碰撞、Skill Commit起CD、Encounter结算、存档/Quest/WorldProgression。
- 不为通过测试而取消、削弱既有测试；拒绝条件要可诊断而非以 `Wait` 掩盖。
- 废弃代码**只有在静态引用、配置引用、动态注册、存档迁移路径全部核实且有测试与负责人批准后**才真正删除。清理后确认源码、Scene、Resource、CSV、JSON没有悬空引用。
- 修复仅覆盖自己更改的范围，提交或交付时附 Git diff 文件列表；不要覆盖他人未提交变更。

## G3｜验证与交付

- 已有对应 C# 测试项目：执行 `dotnet build`、`dotnet test`；测试随机种子、同Tick并列选择、锁敌状态释放、房间反复进出、热更装备属性（若支持）、长时间挂机无泄漏。
- 对 Godot 场景至少检查：进房无明显呆滞；无单位物理卡位；3/5近战初始坦克容量能观察到差异；远程普通攻击行为稳定；召唤物入场/死亡不会令怪物转向抖动。
- 现有原有战斗相关回归不可删除；投射物高速连续命中、AoE、角色死亡、技能CD/EffectQueue、奖励仅结算一次仍须 PASS。
- 缺 Godot 可运行环境则标注 `NOT RUN`，不把 Core 测试当作 Windows 图形实测。
