# Chapter 1（Act I）世界地图、区域、地牢与解锁规则 — Claude Code 开发规范 V0.4

> **目标**：将已经确认的 `Chapter1_Act1_Interactive_Map_V0.3.html` 设计，落成可由 Godot/.NET C# 加载、校验、展示、导航和持久化的章节地图及区域攻略规则。  
> **状态**：第 1 章的区域结构、1 格罗格营地、地块布局、分支解锁原则已获确认；**具体非原典地牢名称、原创 Castle 名称和部分 Boss 是 V0.3 制作占位配置，不等于内容正式定稿**。  
> **交付边界**：本任务集中在**章节大地图与 POI/解锁业务层**，不要求重写随机地牢生成器、战斗、掉落、技能或 UI 全局架构。

## 0. Claude Code 必须遵守的执行约束

1. **T0 只读审计优先**：先检查现有 `Game.Core`、`Game.Godot`、地图/关卡/存档/地牢/战斗接口与当前分支，列出可复用组件和缺口；不得假定这份规范对应的类、配置表或 UI 已经存在。
2. **以配置驱动地图**：章节地块、区域、地牢、要塞、连通关口、依赖图作为外部数据加载；不要将 8×8 数组、33 个入口直接散写在 UI 控件中。项目既有配置方向为 CSV（基础表）+ JSON（复杂结构）；可以基于实际仓库调整拆表方式，但需保持强类型校验。
3. **规则在 Core，表现放 Godot**：解锁判断、通关状态、地牢前置计数、章节完成条件由 Core 决定；Godot 只绘制、反馈并请求行动，不能自行标记关卡通关。
4. **没有大地图战斗**：大地图仅提供地块浏览/行走、区域解锁、地牢和 Castle 入口；真正战斗全部在独立随机生成的地牢/要塞实例中进行。角色小队目前考虑 3–5 人，**人数尚未锁定，不在本任务写死**。
5. **已有战斗/奖励事实不能被地图逻辑回滚**：仅消费经战斗/地牢系统确认的正式完成事件；不造假 Boss 击杀和通关奖励。
6. 先提交审计、方案、字段映射，确认后编码；编码后 `dotnet build`、L1 Core 自动测试、L2 Godot 实机操作测试，分别报告 `PASS/FAIL/BLOCKED/NOT RUN`。不要把设计表本身称为已运行功能。
7. **V0.3 地图 HTML 是经过确认的结构参考，不是应直接导入或在 Godot 嵌入运行的正式游戏逻辑**。如需做必要的数据纠错，单独列出差异，不擅自修改用户确认的拓扑。

## 2. Chapter 1 基础结构与坐标约定

- 章节配置 ID：`ACT01`（建议内部 ID），展示名称：`第一章 / Act I · 罗格营地`（**包装标题可调整**）。
- 大地图：**8 列 × 8 行 = 64 格**，非所有章节通用尺寸。
- 区域：8 个 `REGION_01`～`REGION_08`。
- 营地：`TOWN_ROGUE`，**1 格**。
- 可到达图形地块：**49 格**（8 区域共 48 格 + 营地 1 格）。
- 不可通行：**15 格**，标记 `x`，用于山脊、峡谷、边界。
- 前置地牢入口：**33 个**；统治要塞入口：**8 个**（分别占用一个区域地块）；**41 个 POI**。
- 大地图内网格 4 邻接（上、下、左、右），**不可对角移动**。同区域地块允许相邻移动；不同区域必须存在显式 `Gate` 且目标区域已解锁。
- 本文所有地块坐标均为**1-based `(行,列)`**，例如 `(5,4)` 为第五行第四列。原 HTML `gridRows`、`gates` 采用 **0-based `[row,col]`**，实现转换不得漏减 1。
- 地块可为空地、Dungeon、Castle 或 Town。一个地块最多放 1 个主要 POI；**Castle 不计入本区必清地牢入口数**。

- 上述关口在区域双向通行意义上是**连接关系**；区域未解锁时不能借助返程方向或视觉邻接绕过锁定。区域已攻克后往返策略以现有大地图导航设计为准，具体移动动画速度仍待表现设计。
- **关口 G04-05 的地牢入口 A04-D03 在 `(2,5)`，而边界通道位于 `(2,7)→(2,8)`**；这是 V0.3 美术/拓扑分工：地牢 POI 表示攻略内容，Gate 表示大地图跨区通行位置。不得在 Core 中自动把这两个坐标视为同一个地块。以后若需要“过地底通道直接出现在黑暗森林入口”的转场演出，须单独设计，不影响当前静态解锁图。

## 5. 主线与支线依赖关系（区域 Castle 层级）

```text
罗格营地
   │ 起始开放
   ▼
① 鲜血荒地 [3 必清地牢 → 城堡]
   │ 征服后
   ▼
② 冰冷之原 [5 必清地牢 → 城堡]
   ├─────────────────────────────┐
   ▼                             ▼
③ 埋骨之地 [支线、血乌]        ④ 石块旷野 [主线、崔斯特姆]
   │                             │
   └─ 可独立完成，不阻断主线       ▼
                              ⑤ 黑暗森林
                                 ▼
                              ⑥ 黑色荒地 / 遗忘高塔·女伯爵
                                 ▼
                              ⑦ 塔摩高地
                                 ▼
                              ⑧ 修道院 / 大教堂 → 地下墓穴·安达利尔
                                 ▼
                           Chapter 1 主线通关
```

**当前 Chapter 1 区域 Unlock 依赖表（仅逻辑父节点，实际移动还受 Gate 约束）**：

```text
REGION_01 <- TOWN_ROGUE (default unlocked)
REGION_02 <- REGION_01.Conquered
REGION_03 <- REGION_02.Conquered   [optional branch]
REGION_04 <- REGION_02.Conquered   [main]
REGION_05 <- REGION_04.Conquered
REGION_06 <- REGION_05.Conquered
REGION_07 <- REGION_06.Conquered
REGION_08 <- REGION_07.Conquered
ACT01.MainCleared <- REGION_08.Conquered
```

### 5.1 地牢 / Castle 进度状态机（首版建议的最低业务语义）

- `Locked`：前置 Castle 尚未征服；可以作为地图信息展示，但禁止实际进入 Dungeon、Castle 与未解锁地区。
- `Available`：区域已解锁、允许大地图行走及进入已配置入口。
- `DungeonCleared`：只由真实地牢成功完成事件改变；地牢内部含多层时按完整 Dungeon 的终点成功判定，而不是进入或通过首层就算通关。
- `CastleEligible`：该区域全部 `requiredForCastle=true` 的地牢完成之后成立；区域 3 虽是支线，**它内部仍需 3 地牢全清才能攻打血乌 Castle**。
- `Conquered`：真实 Castle 攻坚流程完成，且对应内部 Boss / 要求已满足；更新本区通关与后继 Unlock。
- `ChapterMainCleared`：A08-C01 内部安达利尔真正被击败，城堡成功完成，区域 8 征服。**不要求先征服区域 3**。

**重复刷取与解锁首次通关是两个不同概念**：`FirstClearFlag`/`Conquered` 作为永久地图进度，与每次临时地牢实例的战斗成败分开存放。是否允许已清地牢或 Castle 无限重打、重打有什么奖励、不同难度继承什么，需按照后续刷宝系统设计，**本规范不擅自决定掉落规则**。

### 5.2 后续章节共同遵循的分支规则

- `Region` 可有多条后继（Fan-out），不必总是单一链条。
- 分支区可以有自己的 Castle、地牢与奖励，但**除非依赖显式声明**，不应自动进入主线后继的 `prerequisites`。
- 主线与支线可能具有不同的重要性，内容表现应体现血乌这类高记忆点，不应因为它是支线就降格成一个普通随机怪。
- 支线与主线可以并行选择攻略顺序，但全章难度层/章节次序规则仍应配置化，不可写死 Act1 的区域数量。
- 依赖图必须是无死锁有向图，门禁与必清副本不能组成 A→B→A 的强制依赖环。
