## 1. 执行纪律

1. **先审计、再核对、再给出设计接口和决策清单。** 不修改正式玩法代码或配置来“修好”审计结果。
2. 所有结论注明证据级别：`STATIC_VERIFIED`、`LOADER_VERIFIED`、`RUNTIME_VERIFIED`、`UNAVAILABLE`、`DESIGN_DECISION_PENDING`。`LOADER_VERIFIED` 不等于逐字段运行验证。
3. 保持「现有事实」「可扩展能力」「建议设计方向」「待批准变更」四类信息分开。
4. 对 M1/M2 的机器台账，**复用而非平行重建**；如发现审计工具字段定义或导出 Bug，只允许修复 `tests/` 审计工具与重新生成其对应数据，报告记录变更前后差异。若需动正式 Core，停止并申请批准。
5. 保留正式城堡玩家手动挑战；模拟可经合法入口模拟玩家行为，不改变正式规则。
6. 不通过占位数值的模拟结果评价星图、编队、天赋等系统的价值高低。

### 内容补全边界

P2-3 的目标是 **维持独立系统总量与主结构不变，先补充正式内容与必要局部规则，再做框架数值设计**。对每一候选扩容项必须分类：
- `DATA_ONLY`：现有表与消费链即支持，可直接在 P2-4 投放。
- `DATA_PLUS_CONFIG_SCHEMA`：需要调整已有配置结构/校验，但无需新运行规则。
- `EXISTING_SYSTEM_EXTENSION`：必须增加既有系统的运行消费者或Effect/事件/AI行为。
- `OUT_OF_SCOPE_NEW_SYSTEM`：本轮不考虑的独立系统。
- `DECISION_PENDING`：待设计批准且已说明原因。

**不要为 P2-3 擅自填入最终节点数、效果、价格、时间目标或技能数值。** 只能提出所需信息、约束和候选工作包。

## 4. M3-C｜三项必须形成专门裁决卡的技术边界

### C1. `floor_plan.csv` 跨章 Schema 与等级权威

已知 act1~5 分别有 40/37/38/41/42 列，12个未被正式读取的字段；`FloorMonsterLevel` 与真正生效的 `MonsterLevel` 并存。

请提交2~3种选择（例如保留现状加醒目标注／统一所有章节 Schema 并显式废弃旧列／为未来内容保留规划字段但改为单独规划表），逐项给出：
- 真正运行消费字段和仅规划字段列表；权威值覆盖顺序与表名；
- 是否会影响现有1515楼层规划记录及生成器；
- 旧表/存档/导出工具兼容成本；
- 最小修改文件范围、风险及推荐方案。

**M3只做裁决提案，不直接修改正式表、删除列或把规划预算接到刷怪。**

### C2. 23个旧 `CastTalent` 节点的正式化路径

依照既有逐节点差异表，分为：
- 可直接改绑定已有正式`skill_id`；
- 需补充正式技能/Effect配置（复用10类已有效果）；
- 需扩展既有Effect/规则；
- 设计上需重新定义而不能等价迁移。

每个节点必须给出行为证据、迁移类别、可能的构筑变化、可观测性与测试要求。不要自动替换当前玩家技能，也不把旧路径当成正式设计要求。

### C3. 星图的扩容能力与跨系统节点边界

面向 P2-3 的长期增量星图专项，形成**能力分类**而非直接设计节点数量：
- 已支持的纯属性和功能节点，以及其成本、前置和等级限制；
- 已存在的属性Key可否通过现有 `star.csv` effect 白名单直接作用？如果不能，需列白名单与消费方扩展；
- 经验/金币效率、职业/技能流派、冒险效率、特殊挂机能力等**候选节点方向**，分别列明可复用消费方、需要新增消费方、是否涉及持久化与UI；
- 新效果与现有系统的耦合度、风险、存档迁移条件。

不批准时不得直接加入新类型、扩大上限或填写价格。

## 5. M3-D｜事件、怪物与战斗观测的交接

1. **地牢事件**：明确现有宝箱/营火的触发与一次性状态；设计表驱动的最小 Schema 与读取/执行/存档/UI 触点，尤其是旧存档 `Room.Event` 的兼容方式；不实施新事件。
2. **怪物/Boss**：明确身份、投放池、行为类型、词缀、Boss技能包、阶段剧本的不同扩容成本；不把34个技能包说成34种独立行为。
3. **FloorPlanning**：记录规划预算仅为报表、运行生成由哪组配置决定；P2-3需要选择是否值得把预算纳入真实生成，不能默认已实现。
4. **`M3_COMBAT_FACTS_PENDING`**：现有无逐技能施放/命中/伤害、攻击者身份、召唤生命周期、城堡失败致死序列结构化事实。提交独立的 `CORE_READONLY_FACTS_PENDING_APPROVAL` 决策卡，列最小事实结构、开启条件、固定容量、无随机/存档影响的证明方式及开关前后业务哈希相同的验收条件。**本轮不得未经批准修改正式Core**；同时注明 P2-4 逐技能核验之前应处理。
