# Steam D2｜P2-3-M1 正式内容蓝图与规模规划｜执行方案 V1.0

**工作编号：** P2-3-M1  
**工作性质：** 正式内容策划准备与规模规划；**只做设计分析与提案，不写正式游戏代码或配置**。  
**阶段位置：** P2-1 模拟环境验收 → P2-2 配置与运行接口审计通过 → **P2-3 内容补齐、必要规则深化、框架数值设计** → P2-4 投放和模拟验证 → P2-5 体验评价。

## 1. 本轮目标与边界

**目标：** 在现有游戏系统总量和总体玩法结构不变的前提下，提出一套可支撑**首版30分钟完整正式内容切片**的内容结构，同时规划**2小时扩展层**与**4小时及以后扩展接口**。明确哪些内容可纯配置投放、哪些需要扩展既有机制，为 P2-3-M2/M3 内容设计与 P2-3-M4 框架数值设计建立统一蓝图。

**优先原则：**

1. **先定内容与规则，再填数值。** 当前测试数值不可用于评价系统强弱、成长价值和正式平衡；允许参考代码规则与技术边界，不据当前 4 小时模拟的Lv/金币来倒推正式设计。
2. **不增加独立系统。** 重点做现有系统内的内容深度：天赋/技能/属性、星图、房间事件、怪物与 Boss、章节/冒险投放、触发/Proc。装备/商店/新养成体系暂不纳入。
3. **星图是核心专项。** 定位为覆盖多个现有玩法系统、长期消耗金币、持续给出下一目标的增量放置成长体系；不允许仅靠重复添加 attack/hp 节点凑规模。可提出新增功能性 effect/消费点，但必须标出代价和实现审批门。
4. **天赋必须从测试内容转向正式 BD。** 五职业、节点结构、主动/被动分支和实用性都要设计；先判断旧节点保留/改写/淘汰，再决定23个旧 `CastTalent` 节点如何迁移，**不得为迁移而迁移**。
5. **玩家规则保持不变。** 城堡正式挑战仍需玩家手动点击；模拟器仅模拟玩家合法操作；自动地牢冒险、手动成长选择和失败重试的既定边界不变。
6. **审计建议不是策划裁决。** 输出推荐项时同时列备选方案、必要依赖、实现成本、需用户批准事项；未审批不标记为最终定案。

## 3. 本轮工作步骤

### M1-A｜正式内容规模分层

围绕玩家可执行的完整循环（自动冒险与战斗 → 收益 → 手动角色/天赋/星图成长 → 城堡主动挑战 → 新区域）分别提出：

- **30分钟正式切片（必须可完整体验）**：应覆盖的职业成长、首次BD分支决策、星图阶段目标、有效怪物/精英/Boss遭遇、地牢事件、城堡推进与反馈。
- **2小时扩展层（明确扩展路径）**：如何进一步铺开职业BD选择、星图分区/长线目标、怪物组合与章节内容；不要求本轮全部制作。
- **4小时及以后（仅留结构与扩展接口）**：星图节点层级、数值容量、章节内容扩展能力；不要求现在制作全部内容。

逐系统分别给出 **现有内容、30分钟目标内容类别与候选数量区间、2小时扩展方向、后续扩展接口、设计理由**。候选数量是**需要策划审阅的提案**，不是直接写入CSV的定额；没有证据不得把模拟时间当作实际玩家时长。

### M1-B｜五个内容重点专项

1. **天赋/职业BD：** 按5职业分别提出职业定位、2–3条候选构筑方向、主动/被动/强化节点角色、必要技能表现与首个30分钟可感知的成长决策；审视技能槽与天赋点供给的衔接。对既有23个旧路径节点标记`保留并正式化/重做/淘汰/待定`，此轮**不进行迁移**。
2. **星图（最高设计优先级）：** 给出“基础增量节点—分支特色节点—关键功能/里程碑节点—长期延伸”的结构候选；覆盖既有编队/技能槽/洗点以及经验、金币、战斗、召唤、冒险效率、职业协同等**候选价值方向**。每种新功能必须说明作用于现有哪个系统、是否已有消费者、是否引入负面循环或不可控乘区、是否需要Core/存档/UI扩展。禁止将全部候选自动判为已批准。
3. **属性/Effect/触发：** 对18个零投放但已有消费者的属性与未投放的Ability/Proc能力，按“有明确BD/星图用途—暂不需要—机制缺失”分类；如提议新增Key或新Effect，列最小代码触点及数据验证前提。审查是否存在互相叠乘导致未来数值不可控的风险（只做结构判断、不填具体倍率）。
4. **地牢事件：** 提出适合自动挂机/观看的事件类别与触发节奏（收益、恢复、风险、变种战斗、特殊发现等候选），明确**不让大量事件取代战斗时间**。区分纯文案/表现扩充与确实需要表驱动Event schema、执行器、存档兼容的项目。
5. **怪物/精英/Boss：** 区分身份、美术外观、AI行为、技能包、遭遇组合及关卡投放。提出30分钟需要的最小战术差异和Boss特色，说明哪些可复用现有行为/技能、哪些才必须新增行为或阶段状态机。不得把49身份、34技能包等同为49/34种有效行为。

### M1-C｜依赖与扩展成本排序

把 `content_work_packages.csv` 的16包重组为**设计上的主线工作包**，不机械地把16包全部当作同等优先级新增开发任务。每项标注：

- `DATA_ONLY`（配置可表达） / `DATA_PLUS_CONFIG_SCHEMA` / `EXISTING_SYSTEM_EXTENSION` / `OUT_OF_SCOPE`；
- 对应现有字段、消费方和运行时限制；
- 工作量档位（小/中/大，解释判断依据）；
- 需产品裁决、需技术审批、依赖 P2-4 观测接口或仅依赖配置；
- 正式内容投放前的最小验收路径。

**依赖要分两类：** `DESIGN_DEPENDENCY`（没有它不能完成设计）和 `VERIFICATION_DEPENDENCY`（设计可先完成，但P2-4执行/验证前必须补齐）。D-13战斗只读事实目前是**后者**，不得错误阻断P2-3的设计。

### M1-D｜设计裁决登记与技术边界

至少单列以下裁决卡，明确保留/推荐/待批准，不能直接执行：

- `D-04`：23旧 `CastTalent` 的内容去留与迁移时机；先设计正式节点，再定最终迁移集合。
- `D-08/D-09`：星图的新增功能类型、长期结构与既有席位/技能槽上限；**不能仅以“当前六类支持”为由排除新功能**。
- `D-10`：房间事件配置化，旧 `Room.Event` 的存档兼容约束。
- `D-11`：Boss 是否需要阶段机制，优先判断能否用现有技能包与事件规则表达。
- `D-01/D-02/D-12`：楼层规划Schema漂移、权威怪物等级字段与预算是否真正驱动生成；原则上不阻断P2-3内容设计，避免提前大改生成器。
- `D-13`：战斗事实结构化采集待技术批准，列为 P2-4 全技能/召唤数值验收的前置，不擅自修改 Core。

## 6. 本轮明确不做

- 不实现23个旧天赋迁移、不扩充星图节点和价格、不填正式攻击/经验/金币/难度值。
- 不新增装备、商店、复杂Loot或独立养成体系。
- 不修改正式城堡手动点击、不修改等级差经验衰减公式、不调整房间布局与楼层生成算法。
- 不因临时测试值下的队伍/天赋强弱差异删改系统。
- 不擅自批准D-13只读CombatFacts Core接口，不将“设计完成”当成“代码已实现”。
