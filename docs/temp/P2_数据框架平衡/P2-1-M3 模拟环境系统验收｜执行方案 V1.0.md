# Steam D2｜P2-1-M3 模拟环境系统验收｜执行方案 V1.0

**阶段定位：** P2-1「模拟测试环境建设」的最终验收关口。  
**前置状态：** M1（入口死锁修复）通过；M2（模拟工具能力审计与补齐）**测试侧通过**。  
**执行对象：** Claude Code，基于实际仓库 `Idle-CRPG/` 工作。  
**本轮原则：** 验证工具、发现 Bug、明确观测边界；**不做数值设计与强弱评价，不修改正式玩法、数值及存档**。

## 0. 已知基线与本轮裁决

1. `SimulationRunner` 已支持 V1/V2 策略、显式星图/编队/天赋计划、20Hz Tick、版本化产物、同 Seed 业务哈希、经验及金币对账、异常分级。
2. M2 已验证全量 Core Checks、Godot headless smoke、A/B/C/D/E/F、同 Seed 复跑；六场金币差额与经验 `unexplained_ticks` 均为 0。
3. **E 的正式精确场景为 `E_min_party.json`**；`E_party_only.json` 是历史近似场景，不得将两者数据混作同一口径。
4. **城堡在正式游戏始终由玩家手动发起**；模拟策略只调用合法 `RequestCastleChallenge`，不代替通关。
5. A 纯挂机在 Lv7 达到等级差经验 0% 平台属当前玩法预期；不能将其定性为运行 Bug，也不能用现行占位数值评价成长系统价值。
6. M2 仍缺**逐技能施放、攻击者、伤害来源、召唤事实、部分失败致因**的结构化数据；本轮先评估是否为 M3 完整验收所必需。未经批准**不可擅自修改正式 Core** 添加观测接口。

## 1. 本轮目标与交付

建立可重复执行的**系统验收机制**，证明模拟器能够：

- 按配置模拟合法玩家操作，并如实记录成功、拒绝、未执行与原因；
- 长时连续驱动真实游戏主循环，发现运行停滞、状态机异常、结算异常；
- 对金币、经验、章节推进、战斗/地牢事件给出可复现的事实和明确的不可观测范围；
- 在多 Seed、不同编队和操作策略下运行，避免单 Seed 偶然通过；
- 为后续 **P2-2 全系统配置盘点**、**P2-3 框架性数值设计**、**P2-4 数值投放验证** 提供稳定的测试入口。

**交付：** 一份统一 M3 Review（Markdown）、可复跑命令、验收矩阵、缺口/风险清单及 M3 放行结论。原始 CSV/JSON 放忽略的 `artifacts/`，按仓库 `AGENTS.md` 输出规范，不复制大量机器数据到 `docs/`。

## 2. M3-A｜先审计验收合同（只读）

在编码前审计 M2 当前代码、配置、运行命令及其测试，不预设缺失。给出 1 张表：**验收项 → 现有实现 → 现有断言 → 未覆盖风险 → 本轮最小补齐**。

至少包括以下 10 个类别：

| 类别 | 本轮应验收的核心不变量 |
|---|---|
| 场景配置 | V1/V2 兼容、未知字段/版本拒绝、非法 ID/周期/重复目标拒绝、默认动作关闭 |
| 玩家操作 | 城堡、星图、编队、天赋与装配走真实合法接口；显式策略精确执行，不多买/漏买、不越级解锁 |
| 主循环状态 | `World → Dungeon → Fight → Loot → Village` 能推进；死亡返村与重试可继续，不进入无法恢复状态 |
| 战斗/入房 | AUD-001/002 永久死锁回归有效；单人/多人、四方向入房；有敌人时不长期卡在门口 |
| 经验 | 升级、整数/小数经验、等级差、事件经验、跨级结算可解释；`unexplained_ticks=0` |
| 金币 | 拾取、卖杂物、星图、洗点与余额闭合；`期初+收入−支出=期末` |
| 地牢/城堡 | 可挑战、请求、排队、正式进入、胜利/失败、区域/章节解锁可区分；不把“请求接受”当“获胜” |
| 异常分类 | `XP_RATE_ZERO`、`MANUAL_GATE`、`COMBAT_FAILURE_LOOP`、`SUSPECTED_STUCK`、`RUNNING`、`UNDETERMINED` 的口径可解释，失败重试不冒充有效进展 |
| 确定性与追溯 | 同代码/同配置/同 Seed 业务产物一致；不同代码/配置可识别；版本/策略/Seed 有指纹 |
| 隔离与资源 | 不写玩家 `user://`；诊断有界；测试输出不参与正式存档；长跑无明显失控增长 |

**重要：** 覆盖“已有系统”，不把未实现的装备、商店等未来内容算作本轮缺陷；新发现的正式逻辑 Bug 单列证据和最小修复建议，不未经审批修复。

## 3. M3-B｜测试增强与分层回归

### B1. 快速定向检查（每次变更均执行）

复用已有 `--simulation-tool-checks`、`--room-entry-checks`、星图/天赋/编队/技能/召唤/城堡/存档等 Core Checks；仅为真实缺口补少量定向断言，不重复造第二套游戏逻辑。

必须证明：

1. V2 `E_min_party` 仅购买 `s_root(1)`、`s_party_1(1)`、`s_party_2(1)`，只编入合法三人，不附加天赋/额外技能装配；非法/未解锁策略给出正确拒绝理由。
2. 开关或策略关闭时无隐性动作；各组周期及同 Tick 只执行一组行为的次序可追溯。
3. 入口死锁回归仍覆盖四方向、多尺寸、1/2/3人及边界浮点案例；已卡旧档可以恢复。
4. 经验和金币每项统计为**发生的事实**，`0` 与 `unavailable` 严格区分。
5. 模拟代码/日志的扩展不改变同 Seed 下正式业务结果（如有差异先解释原因）。

### B2. 标准场景基线（原 Seed）

使用 **Seed `20261023`**，全部运行真实 `GameSession.Tick(0.05f)`：

| 场景 | 游戏时长 | 用途/应成立的性质 |
|---|---:|---|
| `A_pure_idle` | 240 分钟 | 无自动城堡；Lv7 经验平台可合法存在，但**击杀/金币不应因入房 Bug 冻结** |
| `B_guided_progress` | 240 分钟 | 合法成长和城堡推进，验证完整操作链及结算 |
| `C_castle_only` | 240 分钟 | 单人可持续挑战、失败重试；不能把多次失败误判为死锁 |
| `D_solo_growth` | 240 分钟 | 单人合法成长、失败返村与后续继续推进 |
| `E_min_party` | 240 分钟 | 精确最小扩编；验证策略不增加无关成长 |
| `F_policy_probe` | 30 分钟 | 有意触发官方拒绝理由，验证失败操作可观测 |
| `T_tool_probe` | 6 分钟 | 工具快速自检、结构与数据完整性 |

**不使用现行等级/金币绝对值作为 PASS 阈值。** PASS 依据合法性、可追溯性、结算闭合、状态推进及异常解释；数据变化若来自实际代码/配置差异，应记录版本与原因。

### B3. 多 Seed 与边界场景

最低覆盖种子：`1 / 2 / 3 / 7 / 42 / 99 / 20261017 / 20261023`。

- `A_pure_idle`、`C_castle_only`、`E_min_party`：**8 Seed × 240分钟**；关注无故冻结、合法门槛、单人/三人冒险。
- `B_guided_progress`、`D_solo_growth`：至少 **3 Seed × 240分钟**；关注全策略动作、失败重试及状态链。
- 选择至少一个已出现大量全灭/返村的现场，验证“失败 → 返村 → 重试”可持续，不允许重复结算或假进展。
- 至少一组场景**同 Seed 双跑**，比较业务哈希和主要机器数据；不同 Seed 不要求哈希不同，但应分别记录。
- 发现 `SUSPECTED_STUCK` 时自动保存有限现场：阶段、章节/POI、房间、队伍位置/HP、怪物状态、导航目标、入房掩码、最近事件与最后进展时间；必须能复跑定位。

不要求一次性做穷举组合测试。若种子批次耗时或数据量异常，记录成本并缩小采集量，不得为了赶进度关闭核心校验。

### B4. 版本指纹与性能稳定性

- 检查 `metadata.json` 是否能区分**未提交的源码/配置变化**。如果仅记录 `.git HEAD`，增加最小文件指纹或明确 `working_tree_unknown`，不得将不同代码版本的数据宣称可严格对照。
- 记录测试总 Tick、耗时、输出体积、诊断条数/截断、峰值内存或可用的近似值；判定有界，不设置未经校准的固定性能数值目标。
- 所有模拟不接触正式存档；机器数据仅进 `artifacts/`。不得因复跑覆盖用户唯一的证据文件，关键 Review 保留对应版本/Seed/指纹。

## 4. M3-C｜战斗事实采集：审批门，不允许暗改 Core

M2 的 `unavailable` 目前包含：攻击者身份、技能施放/命中次数、逐技能伤害与承伤、召唤生命周期、部分城堡失败致因。这些缺口**不阻断 M3 的模拟器流程与账本验收**，但会限制之后 P2-4 对“全部技能/战斗参数已按设计生效”的逐项验证。

本轮要求 Claude Code **只审计并提交是否必需的判断**：

1. 先列出现有 Core Checks、快照和诊断已经能验证的战斗机制与数值；明确哪些确实无法结构化归因。
2. 如必须增加采集，仅提交**最小只读 Core 事件接口方案与影响范围**：建议在 `SettleDamage`、`GrantHeroExperience`、`SkillRuntime.Commit`、`SummonEffect` 等正式结算处读取实际事实；默认关闭、测试入口开启、固定容量或逐 Tick 及时消费、不入存档、不改变随机数与动作次序。
3. 提案说明每项字段、事件来源、性能成本、丢事件/环形缓冲覆盖风险、开关隔离，以及“开启/关闭采集后业务哈希一致”的验证方法。
4. **未经用户单独批准不得实施正式 Core 修改。** 报告中将其标为 `CORE_READONLY_FACTS_PENDING_APPROVAL`，并列出 P2-4 依赖。

不要为了拿全量技能数据而新建并行伤害计算器、埋点平台或无限逐 Tick 日志。

## 5. 结果分级与最终验收口径

每项结论只允许：`PASS / FAIL / UNAVAILABLE / NOT_APPLICABLE`，另注明证据（测试名、场景、Seed、数据文件/字段或代码位置）。不得把未采集写成 0，不得把命令退出 0 等同于没有运行异常。

### M3 放行条件

- 配置合法性、玩家行为精确性与隔离检查 PASS；
- 全量 Core Checks、Godot headless smoke、关键房间入场/存档检查 PASS；
- 标准场景以及规定多 Seed 批次完成，异常均有分类或明确未判定原因；
- 金币差额 0、经验无无法解释结算（若存在，必须定位并修复后重验）；
- 同 Seed 同版本复跑一致；报表版本/策略/Seed 可追溯；
- 不存在**已确认**的永久冻结、重复结算、静默跳过合法操作、玩家存档污染等 P0 阻断；
- 未观测到的逐技能指标明确标 `UNAVAILABLE`，并给出 M3-C 的审批提案与对 P2-4 的影响。

**判定分两档：**

- `M3_TEST_ENV_PASS`：模拟器、合法玩家策略、主循环、账本、异常检测与确定性验收通过，可进入 **P2-2 全系统配置盘点**。
- `M3_COMBAT_FACTS_PENDING`：若只读战斗事实仍缺失，允许并行进入 P2-2，但**不得宣称已具备 P2-4 全技能逐项数值核验能力**；待用户批准专项补齐并回归。

如果存在 P0 FAIL，M3 不放行；提供复现、最小修复方案和新的验收结果，禁止以调数值方式掩盖 Bug。

## 6. 执行边界与交付格式

**允许：** 调整/新增 `tests/Simulation/**`、`tests/*Checks.cs`、测试运行命令、自动统计与 Review；必要时补充只读测试辅助函数。先审计，按最小差异修改。

**未经批准禁止：** 修改正式 Core、正式配置及数值、经验衰减、城堡手动规则、英雄/怪物/技能机制、存档结构；修改旧版 A/B/C/D/E 场景既定含义；开发任何新玩法。

交付 **一份统一 Markdown Review**，建议名称：`YYYY-MM-DD_HH-mm_data_p2_1_m3_simulation_acceptance.md`（严格以仓库现行 `AGENTS.md` 为准）。内容必须包含：

1. 变更文件/未变更边界与真实环境版本；
2. M3-A 十类覆盖矩阵；
3. 快速检查、标准场景、多 Seed 及重复复跑结果；
4. 精确策略执行、金币/经验对账、异常分类与停滞现场；
5. 性能、隔离与指纹结果；
6. 未覆盖指标、M3-C Core 只读采集审批提案；
7. `M3_TEST_ENV_PASS/FAIL` 与是否可启动 P2-2 的明确裁决。

末尾附可复跑命令和原始数据目录；**只交统计报告，不在正式数值上做强弱评价**。
