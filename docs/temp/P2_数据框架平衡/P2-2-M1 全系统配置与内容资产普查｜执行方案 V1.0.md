# Steam D2｜P2-2-M1 全系统配置与内容资产普查｜执行方案 V1.0

**阶段：** P2-2｜全系统配置结构盘点与扩展能力审计  
**里程碑：** M1｜全系统、正式配置和现有内容资产普查  
**执行对象：** Claude Code（在真实 `Idle-CRPG/` 仓库执行，以最新仓库为准）  
**依据：** 2026-10-23《P2-1-M3 模拟环境系统验收》；《P2-2 全系统配置结构盘点与数值接口规划 V0.1》；最新用户设计决策。  
**状态：** 可执行。M3 已给出 `M3_TEST_ENV_PASS`。  
**任务性质：** 只读资产审计、分类、全量建账；不做数值设计、不改正式配置、不扩充正式内容。

## 0. 阶段定位与后续工作边界

完整设计链：

1. **P2-1（已通过）：** 建立可信的模拟/自动化测试环境。
2. **P2-2（当前）：** 盘清现有实际系统、内容ID、配置来源、机制消费链和扩展边界。
3. **P2-3：** **先补齐既有系统的正式内容与必要内部规则，再设计全系统数值**。重点为正式天赋树与BD、星图长期增量体系、属性/Effect表达能力、地牢事件、怪物/精英/Boss；维持既有独立系统总量，不随意新增装备/商店/新养成。
4. **P2-4：** 内容/数值实际投放，逐项验证设计值→配置→加载→运行→模拟结果。
5. **P2-5：** 预期与运行结果对齐后，进行真实体验评价。

**M1 的核心目标：完整回答“工程里到底有什么、哪些真的启用、还有多少内容、现有机制能扩充到什么程度（初判）”。** 不要求现阶段数值合理；不得据占位数值判断任何系统强弱。

### 本里程碑边界

- 可阅读正式 Core、UI、配置、测试、`AGENTS.md`、现有技术文档；可新增只读盘点脚本、审计数据和归档报告。
- 不修改生产 `Scripts/**`、正式 `config/**`、场景、存档、战斗规则、经验衰减、手动城堡门槛、模拟策略和现有断言。
- 不在 M1 实现新节点、属性、技能、怪物、事件、Boss、Effect 类型。
- 发现 Bug、死配置、硬编码、配置覆盖或技术风险，**记录证据与建议，不擅自修复**。
- **禁止**将未实现的规划内容记为已生效；也不能因为尚未观测到逐技能事件，就把已实现的技能写成“未实现”。

## 1. 执行顺序：先审计加载路径，再枚举资产

### M1-A｜实际仓库、配置路径和系统清单

1. 读取仓库 `AGENTS.md` 和现有配置字典/审计文档，确定允许的归档位置、命名与脚本规范。
2. 从正式启动入口 `Main._Ready`/`Config.Load`、章节加载器、`LegacySkillConfig.Load`、存档恢复、测试专用 `SimulationRunner` 等**实际代码调用路径**向下追溯，不以目录名字猜正式生效范围。
3. 生成**全部配置文件清单**（CSV、JSON、Godot Resource及存在的其他格式）：相对路径、文件类型、正式/预览/历史/测试属性、加载器、优先级、SHA256、记录数、字段数、缺表/回退策略。
4. 生成**实际系统及子机制清单**：系统ID、功能/状态机入口、状态持有者、生产配置来源、测试入口、运行状态及数值相关性。
5. 专项区分 `chapters/act*/` 正式配置、根目录旧表、`legacy/`、GM预览与测试夹具；重复名字不得视作相同来源。

状态分类统一使用：

- `ACTIVE`：当前正式运行链生效；
- `PARTIAL`：仅部分行为正式生效；
- `PREVIEW_ONLY`：仅GM/隔离预览；
- `LEGACY`：旧运行链或历史兼容；
- `TEST_ONLY`：只供模拟/回归；
- `PLANNED_ONLY`：有明确策划规划但尚无生产实现；
- `UNVERIFIED`：暂无法核证（必须说明缺什么证据）。

不存在的内容不得占用已实现清单；需要时另列 `NOT_FOUND`。

### M1-B｜全量内容ID与实际投放普查

**必须遍历全部有效配置，而不是抽5个例子。** 至少覆盖：

| 内容域 | 必查内容与关系 |
|---|---|
| 英雄/编队 | 五职业定义、解锁条件、基础技能、编队上限与入口 |
| 属性/战斗规则 | 正式可用属性名、Modifier/Buff/Effect效果种类、伤害类型、通用触发和基础公式入口 |
| 天赋/技能/BD | 每职业全部天赋节点、行列/前置/等级、主动与被动、`skill_id`及旧 `CastTalent` 路径、技能效果引用、运行状态 |
| 星图 | 全部节点ID、最高等级、价格表、前置/连接关系、效果类型、编队/技能槽/洗点等功能性节点和属性节点 |
| 召唤 | 定义、召唤物ID、容量/上限/持续时间、技能引用、召唤与跨房规则 |
| 怪物/精英/Boss | 五章身份、行为模板、技能包、精英词缀、Boss配置、投放池、正式投放/仅预览 |
| 地牢/房间事件 | 生成与房间类型、实际房间事件ID/奖励/条件/运行入口、清房/拾取/楼层/城堡事件链 |
| 世界与关卡 | 五章区域、POI、章节解锁、挑战档、难度、楼层表、配置计划与实际生成的关系 |
| 经济与成长 | 经验、金币、杂物与自动售卖、宝箱/事件奖励、星图消费、洗点费用、可见成长入口 |
| 运行与表现参数 | AI/接敌/入房/移动/镜头/时间/存档中影响正式体验节奏的配置及重要常量 |
| 额外发现 | 任何从生产加载入口与消费代码发现、上述未列出的机制或内容 |

每条 `content_registry` 至少登记：`content_type, id, source_path, parent_id, referenced_by, deployment_scope, runtime_state, active_evidence, duplicate_id, dangling_reference, remarks`。

严格区分：**“配置文件有记录”≠“被生产加载”≠“正式游戏有机会生成/触发”≠“在模拟中已经观察到”。** 证据按这四层标记。

特别核验：`FloorPlanning` 预算≠实际 `Reveal` 刷新数量；旧审计报告中的数量（如星图17节点、天赋61节点）仅为历史对照，不作为最终统计值。

### M1-C｜内容扩充能力初步调查（为 P2-3 服务）

本项为本轮新增的重点。**M1 做结构/约束初判，机制读值与Effect运行链的深入实证留待 P2-2-M2。**

| 专项 | M1至少回答的问题 |
|---|---|
| 正式天赋树 | 每职业节点数量/拓扑的配置容量；行列/等级/槽位/前置有无代码固定上限；增节点是否只要数据；技能/被动种类是否能覆盖计划BD |
| 属性与效果表达 | 生产支持哪些属性Key、Modifier操作、Buff/Effect/Trigger、伤害与抗性种类；新增一种属性/效果大致需要修改哪些层；哪些只是命名未实现 |
| 星图（重点） | 节点总量/拓扑/等级/价格规则；已经支持的效果种类和跨模块解锁；能否纯配置增加节点；新功能性节点是否需要代码消费方；金币出口如何接入，但**不设计价格** |
| 地牢事件 | 正式事件种类/触发/结果接口、奖励与风险表达、固定房间类型限制；增加事件数据是否即可运行，还是需要独立行为实现 |
| 怪物/Boss | 身份与行为分离、怪物池/技能/精英/阶段支持；新增身份与新增行为逻辑的成本差别；真实内容投放状态 |
| 关卡/地图 | 章节、POI、怪物投放引用和难度配置的可扩展性，规划参数是否实际驱动运行 |

给每类扩充需求打上**证据支持的初步标签**：

- `DATA_ONLY_CONFIRMED`：既有同类型案例和读取/消费链表明可纯配置扩充；
- `LIKELY_DATA_ONLY_NEEDS_M2`：初判可数据扩充，但尚缺完整运行链确认；
- `REQUIRES_EXISTING_SYSTEM_EXTENSION`：不新增独立系统，但需要在现有Core中增加属性/效果/事件等表达能力；
- `UNSUPPORTED_OR_UNVERIFIED`：当前无支持证据；
- `OUT_OF_SCOPE_NEW_SYSTEM`：会引入新独立系统，本轮只登记不设计。

**不可为了给标签填绿而假定引擎通用化。** 每条结论至少给出对应配置字段/消费者位置/现有内容案例中的一种或多种证据。

输出一份 `content_expansion_gaps.csv`：`gap_id, domain, current_support, content_shortage, proposed_direction, expansion_class, evidence, requires_M2_verification, impact_on_P2_3`。其中 `proposed_direction` 只表达可能补什么**类别**，不在M1具体设计节点或数值。

## 2. 机器资产与报告合同

按仓库最新 `AGENTS.md` 确定最终正式相对路径与命名，**最终机器字典必须持久保存，不得仅在忽略的 `artifacts/` 中**。推荐交付：

1. `system_inventory.csv`：全量系统/子机制和生效状态；
2. `config_manifest.csv`：全量配置文件、来源范围、加载/回退、指纹与格式规模；
3. `content_registry.csv`：全量内容ID、引用、有效投放与异常；
4. `content_expansion_gaps.csv`：天赋、星图、属性/Effect、事件、怪物/Boss等扩容边界与缺口；
5. `issues_and_decisions.csv`：只记录可证实的冲突、疑点和未来裁决依赖，包含`gap_id`/证据/影响/建议；
6. **一份统一 Markdown Review**，按`YYYY-MM-DD_HH-mm_data_p2_2_m1_inventory.md`命名（若仓库约定不同以其为准）。

M1 不必提前产出 M2 才能做的完整 `parameter_registry.csv` 或 `formula_dependency.csv`；但必须为这些下一阶段资产保留可追溯的文件/ID/来源。

报告必须包含：

- 仓库/配置/源码版本指纹，工作区状态能否核实；如 `git` CLI 不可用，明示 `unknown`，不得假称清洁提交。
- 实际扫描和人工复核方法、每类发现总数、活动/预览/legacy/test分类计数、重复ID/悬挂引用/未验证项。
- **按系统列出的正式内容规模与缺口**，重点突出五职业正式天赋树、星图、可用属性/Effect、地牢事件、怪物/精英/Boss。
- P2-3 内容补全建议的**候选工作包及其数据扩充/代码扩展分类**，不提前设计正式内容数量与数值。
- 与 M3 模拟观测边界的连接：缺逐技能/攻击者/召唤结构化事实标记为 `M3_COMBAT_FACTS_PENDING`；不要求本轮修改 Core。
- 已覆盖范围、遗漏与下一步 P2-2-M2 任务清单。

## 3. 验收口径

1. **生产加载来源覆盖率100%**：每条正式加载路径都有文件/默认值/回退说明；不明来源单独标`UNVERIFIED`，不得算覆盖。
2. **正式运行系统覆盖率100%**：不遗漏实际存在的功能子机制；需要自动发现与关键入口人工核对的双重证据。
3. **内容ID登记率100%**：对活动配置枚举所有ID并校验可验证引用；未进入正式投放的独立分类。
4. **M1重点扩容专题齐全**：至少天赋、星图、属性/Effect、地牢事件、怪物/Boss五项都有内容规模、约束初判、证据和M2待验证点。
5. **数据资产可复跑**：同一代码/配置输入能重现清单；重要计数可以从机器表核对，不要求人工复制海量行到MD。
6. **不混淆实现与可测**：M3 `UNAVAILABLE` 不当作零或未实现；自动化测试通过不等于所有机制已经有正式数值设计。

若未达全覆盖，仍交付现有成果，但必须标 `P2_2_M1_PARTIAL` 并说明漏项、阻断原因和最小补查计划。若达到则标 `P2_2_M1_PASS`，**仅放行 P2-2-M2，不等于 P2-2 全阶段完成**。

## 4. 关键样本的人工交叉核对

在全量机器扫描之外，至少人工核对下列跨文件链路：

- **天赋：** 英雄→天赋节点→正式技能/旧行为→效果定义及是否生效。
- **星图：** 节点ID→布局前置→节点价格/等级→已支持的效果消费者（特别是功能解锁）。
- **怪物：** 章节/区域/POI→投放池→行为/技能→实际生成（计划不等于运行）。
- **地牢事件：** 事件配置/枚举→触发入口→奖励或状态变化；只有预览时需明确。
- **属性：** 属性Key→默认/配置→有效值聚合→至少一个运行消费者。
- **正式/legacy：** 加载入口确认五章生效数据，没有混淆根目录旧表。

以上核对中，M1能确认“有加载/消费链”时写`STATIC_VERIFIED`；需模拟观察才能确认时写`RUNTIME_VERIFICATION_PENDING`，在M2进一步落实。

## 5. 执行流程与最终回复

1. **先只读审计**：报告预期文件扫描范围与已有工具，确认无需重复实现审计器。
2. **完整枚举与分类**：按 M1-A/B 输出四份结构化资产（含扩容缺口表）和Issues表。
3. **手动证据复核**：验证关键引用、正式投放和配置覆盖；发现无法确认的记录而非猜测。
4. **最小检查**：运行仓库已有相关加载/配置/引用验证测试；如果无需改源码，不强制完整4小时模拟。若新增只读生成脚本，确认不会写正式配置与玩家存档。
5. **统一 Review**：给 `P2_2_M1_PASS` 或 `P2_2_M1_PARTIAL`、文件路径与计数、未解决问题和P2-2-M2执行建议。

**禁止顺带启动 P2-3 正式内容创作、P2-4 数值投放或测试用Core观测接口。** 如果发现需要改变生产加载器/规则才能达到 M1 覆盖，先提出独立审批。

---

**交接重点：** M1结束时我们应该知道“当前游戏有什么、它从哪里加载、正式投放了多少、未来哪些类型可只填内容、哪些扩充必须拓展旧系统能力”，但不应该已经开始评价现有占位数值的强弱。
