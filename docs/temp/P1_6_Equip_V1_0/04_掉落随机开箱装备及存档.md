# 04｜Loot → OpenChest → ItemInstance → Equip → Save/Load 全链路

## A. 正式已批准流程，绝不重建

```text
BattleSimulation 唯一 KillFact
  → GameSession / Loot 判定是否掉宝箱（判定仅一次）
  → ChestInstance 进入有限 ChestStorage
      └─ 满仓时「战斗继续，额外宝箱丢失且不补发」
  → 玩家明确手动 OpenChest
  → 验证箱资格/物品奖励配置，使用确定性 RNG 准备奖励与词缀实际结果
  → 成功提交：原子地消费箱、将固化属性的新 ItemInstance 加入唯一权威池
  → Equip/Replace/Unequip 在合法 Core 安全边界原子更新槽位引用与来源
  → Save 保存 ItemInstance 已确定数据 + Slot→ItemId + 必要 Ledger/RNG/版本
  → 新进程 Load 验证引用并重建 Modifier/SkillModifier/Trigger listener
```

- 本轮扩展的“装备词缀抽取”只能属于 OpenChest 原子事务内的**装备实例准备阶段**。`ChestInstance` 不应提前持有正式已掷好的随机装备实例，除非未来单独批准新的奖励锁定时点。
- 生成失败不扣箱、不新增 ItemInstance，不能用重复错误操作重抽出好结果。可依现有 RNG 回滚、单次候选流水等 S3 已有设计实现；具体事务技术先审计，不自选正式随机策略。
- 复演 `TEST_ONLY` 战斗不得向真实玩家背包发奖；同一合法新战斗可再次获得新宝箱，不应被旧 KillFact Ledger 阻断。

## B. 随机词缀生成：建议最小结构

`ItemDefinition` / `AffixPool` / `RollPolicy` / `ItemInstanceAffix` 是语义名称，实际工程如已有等价类型**必须复用**。

1. 获取本次开箱奖品的合法 ItemDefinition、奖励可用池及已有上下文（宝箱类型、章节、难度等）。**具体池选择/难度权重 TBD**。
2. 校验权重表、适用 ItemTags、职业或技能标签、排他组、允许数量；未知模板/字段/非法概率报错，不以空词缀静默回退。
3. 在同一次合法 OpenChest 的受控 RNG 中生成所选词缀及各自实际数值。
4. 成功提交时，固化所有已抽出的词缀 ID、值、引用；之后穿戴/换装/重启不再掷骰。
5. 展示层仅渲染固化内容，不由 UI 计算正式装备属性。

**强约束**：`data/` 的测试池“允许一个武器/一个防具，每件至多若干测试词条”只为演示。正式品质（普通/魔法/稀有/传奇/套装）、前后缀分布、词缀个数、权重、总掉率均属 **TBD-05**。

## C. 随机的可复现性与反刷

- 两次独立合法开箱允许不同结果；相同测试 Profile + RNG + 业务命令次序应复现一致的生成结果。
- 相同箱重复点击第二次不生成物品；开箱失败/回滚不能产生新的免费抽奖机会。
- 同一 ItemInstance 重复 Equip/Unequip/Load 不改变已经生成的 affix rolls。
- 使用新版本 AffixDefinition 时旧已生成实例的兼容策略、被移除词缀引用、版本缺失时的错误策略需在修改 Save DTO 前经审批。

## D. 战斗中换装边界

S4 已确认：战斗中可换装，但必须在**确定性安全边界**生效，且整套旧/新来源一次切换，不打断 Action、不重启技能 CD、不追溯已受理 DamageRequest。

以下在 S4 仍待定，P1-5 **不得替 S4 偷定**：

- 当前 Tick 还是下一 Tick / 具体 phase 应用装备请求；多命令先后。
- Windup 期间换装，后续 Commit 是新还是旧攻击属性。
- 已发射尚未命中的 Projectile 的伤害快照时点。
- 有效 Buff/Proc/召唤 SkillSpec 是否立即重建或等待什么安全边界。
- 正在触发的 Proc 的来源装备在同 Tick 已卸下时，取消还是完成既有已入队 Effect。

遇到这些案例必须输出 **局部冲突 + 不同备选 + 对存档/回归影响**，先实现无争议路径，不编造默认行为。

## E. 恢复后注册恰好一次

- 保存权威 `ItemInstance` 固化结果和 `CharacterEquipment` 引用；Derived FightAttr、EffectiveSkillSpec、Proc listener 的运行时对象**不得作为第二份可编辑真值**。
- 读档先检查：实例存在、槽位类型合法、同一 ItemInstance 不在两个槽/两个角色重复占用、词缀定义引用存在、roll 数据合法。
- 只读加载失败必须可见地报错；不能把坏数据当作空白新档，自动丢失玩家物品。
- 成功读档后建立正确的 AttributeModifier/SkillModifier/TriggerRule Source；反复重建不双重注册。
- 真正验收需要**保存磁盘→退出原进程→新进程启动→加载→确认装备与战斗一致**。

## F. 示例配置不能污染生产

所有 `TEST_` 示例都不应与生产 drop tables、正式 ItemDefinition 或存档迁移工具共用同一发布环境。用 Game.Core.Tests 的隔离 Profile 注入，不借 Godot Inspector 直接改全局正式设置。
